> **假设**（未验证的推论）。§11 把它们分开列。

## 0. 一句话

新增一个只读模块 `autotuner/research/search_analysis.py`：把一个搜索运行从台账里读出来，
**排序**、说明**这个样本是不是采样器提出的那个样本**、并**导出**获胜配置——导出的文件
必须能自证它就是获胜试验跑过的那个配置。

它回答三个操作者真的会问的问题：

1. 哪个配置最好，凭什么？（§3）
2. 我这次搜索够大吗？（§5）
3. 这个导出的文件，一周后还能证明它是对的那一个吗？（§6）

它不回答"下一次采样抽哪里"（任务 7）、也不回答"这次剪枝剪得对不对"（任务 5）。

## 1. 边界

### 1.1 只读

模块**不写台账**：没有一处 `TrialLedgerStore.append`，不定义任何新记录类型。理由是两条，
第二条是本仓库实测过的：

- 台账记录的是**搜索做了什么**，导出是**对结果的一种解释**。把解释写进事实层，事实层就不
  再是事实层。
- **在 `search_run` 头之前写任何记录，会让整根台账永久不可读**（任务 5 实测）。读码定位：
  `_validate_layout`（`hyperparameter_search.py:574-622`）共六个抛出点——
  `unknown_layout` 四个（`:586`/`:591`/`:596`/`:608`，`raise` 语句的行号；异常码字面量在各自
  下一行 `:587`/`:592`/`:597`/`:609`）、`duplicate_close` 一个（`:603`）、
  `trial_after_close` 一个（`:619`）。"在头之前写入"命中的是 `:590-594` 那一条
  （`appends[0] != 0`）。本模块没有任何理由承担这个风险。

（补一句以免读者误解：读码确认 `_validate_layout` 的"关闭后扫描"只收集
`record_type == "search_trial"`（`hyperparameter_search.py:613-622`），所以在试验事件之间/之后
写一个**非 search** 类型的记录并不会破坏布局。即便如此，本模块仍然一条都不写。）

### 1.3 不 import 剪枝层

`prune_summary` / `verify_decision` / `PruneSummary` **不 import**（只 import 上面那四个纯函数）。
理由不只是"分工"：`prune_summary` 读的是 `ledger.trials(run_ref=run_ref)`
（`search_pruning.py:988-990`），在降级读的场景下，那**可能是比本模块排序的样本更小的另一批**。
一份"排这批、引另一批的审计"的报告，正是本模块存在的意义所要防的那类缺陷。
被剪的试验在普查表里按状态出现、在 `unranked` 里按序号出现，外加一条 caveat 指明
"想知道每次剪得对不对，去问 `search_pruning.prune_summary`"。

### 1.4 不做（non-goals）

1. **不是贝叶斯采样器**（任务 7）：没有代理模型、没有采集函数、不构造 `Sampler`、
   不调用 `build_sampler`/`replay`。`is_observation`（`:509-516`）在 docstring 里提一句
   "这是给任务 7 现成的判据"，本模块不调用它。
2. **不是剪枝**（任务 5）：不决定停任何东西，见 §1.3。
3. **没有"降级也能导出"模式**：`analyze()` 会**描述**受损台账，但 `export_best()` 拒绝一切

4. **不提供第二个打分通道**：不做"调用方传 `scores` 映射"。本仓库没有任何东西把试验映射到

   （§3.3），并且被记录在报告与回执上。
5. 不修台账、不裁剪、不改写、不迁移、不治撕裂尾行、不定义新记录类型。
6. 不跑训练、不调 `TrialRunner`、不碰 GPU / 后端 / 日志 / 网络。所有测试离线跑。
7. **不做多运行对比**，不跨 run 排名。一次分析一个 `run_ref`：跨运行排行榜是另一个问题，
   它有自己的样本量与空间可比性语义。
8. **不计算网格覆盖率百分比**、不算"还有多少点没试"：那需要空间与完整枚举，会撞
   `_MAX_GRID_TRIALS`，而且报出一个台账从未记录过的数字。本模块只用采样器**自己的** stats
   回答"够不够大"（§5）。
9. **不画图、不渲染文本报告**：渲染层是"第二份可能与记录不一致、且无法 diff"的东西。
   将来要就写成 `SearchAnalysis` 的纯函数，放在本模块旁边，不许再读别的东西。
10. **不替调用方决定方向或排名键**，不从 metrics / observations / stop_reason / 日志里
    反推一个 objective。
11. **不重开、不修复、不续跑**运行：打开的保持打开，被放弃的保持放弃。续跑是
    `SearchTracker.run(retry_interrupted=..., retry=...)`；一个开始重跑试验的读取器就是
    第二写者。
12. **不用 `SearchLedger.orphan_dirs`**：那个诊断分不清"崩了又重跑的目录"与"从未记录过的
    目录"（`:833-879`），报告无从据此行动。
13. 不建目录；**不删任何不是这次调用自己写出来的文件**：输出目录与回执目录都必须已存在，
    与 `write_injection` 的拒绝一致（`config_injection.py:408-409`）。
    （订正于 2026-09-15：计划写的是"不删任何东西"，落地后不成立——写出配置之后一旦拒绝或
    失败，`_discard()` 必须把**这次调用刚写的那个文件**撤掉，否则盘上会留一份半成品配置，

14. **不改任何既有文件**：不改 `hyperparameter_search.py`、`trial_ledger.py`、

## 2. 读侧：为什么必须走 `run()`（并纠正一句我自己写错的话）

**先说纠正。** 本稿的第一版（以及三个候选设计）都写着"`ledger.trials()` 不跑布局校验"。
**这句是错的**，而且错得有来源：`trials()` **自己的 docstring 就写着**
"This is a filter and does not run `run()`'s layout checks"（`:735`）——它说的 "run()'s
layout checks" 指的是 `run()` 里的**运行级**检查，不是 `_validate_layout`。
两个东西共用了"layout checks"这个名字，本稿的第一版就踩在这上面。

读码真相：`trials()` 第一行就是 `self.refresh()`（`:736`），而 `refresh()`
调用 `store.events(verify=True)` 再调 `self._validate_layout(events)`（`:557-572`）。
所以 `trials()` **确实**跑哈希链与 `_validate_layout`。真实差距更窄、也更值得写清楚：

| 检查 | `trials()` / `terminal_trials()` | `run(run_ref)` |
| --- | --- | --- |
| 哈希链 + `_validate_layout` | 跑（经 `refresh()`） | 跑 |
| 撕裂尾行（`trial_ledger.py:617-623`，**不受 `verify` 门控**：`verify` 在 `_read_events` 里直到 `:646` 才被引用，撕裂检测在它之前） | 抛 | 抛 |
| **`_trials_of()`（`:655-683`）**：run_ref 一致、plan/space 指纹一致、序号 1..N 连续、无重复 `assignment_key` | **不跑** | 跑 |
| **`_check_counts()`（`:706-726`）**：`trial_count == stats["proposals"] == len(trials)` | **不跑** | 跑 |

**规则：排序的样本只能来自 `run(run_ref)`**，理由是右列那两组**运行级**检查。
这不是措辞洁癖，它直接决定了 §5 的降级策略能不能存在：序号断档、重复 `assignment_key`、
计数不符这三类失败下，`trials()` 仍然返回记录——**所以"有东西可描述"**，只是不能拿来排名。

### 2.1 三次尝试的读法

```
run(run_ref)
  ├─ 成功且 complete              -> sample_trust="counts_checked"
  ├─ 成功但 complete=False        -> "layout_checked"（打开/被放弃：运行级检查跑了，计数没跑）
  └─ 抛异常
       └─ runs() + trials(run_ref=...) 兜底
            ├─ 成功                 -> "layout_checked"（覆盖运行级失败）
            └─ 再抛                  -> "unreadable"
```

兜底自己的边界也写清楚：因为 `trials()` 会经 `refresh()` 跑布局校验，**布局坏或哈希链坏时
兜底同样失败**，报告如实写 `unreadable`，不假装。撕裂尾行时**没有任何公开读会返回部分试验
列表**，所以唯一拿得到的计数是 `store.summary()["event_count"]`
（`trial_ledger.py:723-750`——注意是 `trial_ledger` 里的 `TrialLedgerStore.summary`，
不是 `hyperparameter_search.py` 的 `SearchLedger`；后者的 `run()` 在
`hyperparameter_search.py:690-700`。实测其键为 `chain_verified / event_count /
events_filename / events_path / incomplete_tail_bytes / integrity_error / latest_event /
root / schema_version`），本稿只承诺这个数，不承诺一个 API 读不出来的数。

### 2.2 `analyze()` 的 except 子句

照抄 `search_pruning.py:991` 的形状**并写出理由**：`except Exception as error:  # noqa: BLE001`，
变量名 `error`。理由不是"防御性编程"，而是本模块的头号承诺就是"台账的事不抛异常"，
一个 `OSError`（路径不可访问、编码错误）若逃出去，承诺就变成了"只对某些异常成立"。
配套测试要求**非 `SearchError` 形状的读失败也产出报告**（测试 A5 / A6 之一，见 §9）。

## 3. "最优"的定义

### 3.1 默认按记录的 `objective`

不是拍脑袋：`TrialOutcome.objective` 的 docstring 自己写着它是"代理模型的 y，而不是从
metrics 里猜出来的东西——猜错是看不见的"（`hyperparameter_search.py:199-202`，读码）；
它也是唯一在**写侧与读侧折叠时都**校验有限性的打分字段（`:444-445`、`:213-217`，
`_folded_trials` 会重新 `model_validate` 一次载荷，`:624-638`）；而任务 4 明确把这个字段的
权威性留给了调用方（`docs/P4.4_task4_design.md:758`）。所以本模块**不得**用"悄悄退回某个
metric"的方式把自己变成那个推导者。它是**默认值**，不是硬绑定。

### 3.2 方向必填，没有默认值

```python
RankingRule(key: str = "objective", direction: RankDirection)   # direction 无默认
```

**实测**：在 `autotuner/research/*.py` 里 grep `maximize|minimize|higher_is_better|direction`，
只命中 `gate_calibration.py` 里无关的 gate 方向名（`:6`、`:141-142`、`:152`、`:343-344`），
以及本模块自己的 `RankingRule`（订正于 2026-09-15：写这句时本模块还不存在，落地之后
这条 grep 必然也命中 `search_analysis.py` 自己）；
`TrialOutcome`、`TrialRecord`、`SearchRunRecord` 上**没有任何字段**记录"这个 objective 是要
越大越好还是越小越好"。

一个有一半概率是错的默认值就是一根看不见的配置线，而它的失败形态——
**把最差的配置当成最好的导出去**——直到有人在上面训练之前，与成功无法区分。所以调用方必须
说出来，报告存进 `rule`，导出回执再存一次，没有任何代码路径去猜。

（这是本设计对"最小方案"那版设计的**覆盖**：它写的是 `maximize: bool = True`。）

### 3.3 按指标排名：可选、显式、留痕

`rule.key != "objective"` 时，它是一个指向 `record.metrics` 的**点分路径**，用
`search_pruning.metric_value` 解析——于是扁平路径与嵌套路径都能用，而且**存在台账里的非有限
读数字符串（`"nan"`/`"inf"`/`"-inf"`）会被还原**，不会被当成缺失（`metric_value` 是
`canonical_metric` 的文档化逆函数，台账写路径是 `model_dump(mode="json")`，
`trial_ledger.py:565`，实测）。

三处把这件事说得很响：`RankedTrial` 同时带**排名用的数**与**记录自己的 objective（逐字，
可能是 `None`）**；`rule` 与 `rule_fingerprint` 同时存在报告与回执上；`key != "objective"` 时
追加一条 caveat，字面就是"这是按 X 排的，**不是**按记录的 objective"。

为什么支持而不是拒绝：拒绝只会让调用方去改台账再来一遍；给一条有名有据的通道更强。
为什么不做默认：`metrics` 是没有类型约束的袋子，键的含义是产品的业务；默认按它排名等于
从一个名字里推断语义，而这种推断错的时候是看不见的。

### 3.4 `None` 从不被强转，且没有"最差分"策略

键为 `None` 或非有限的试验**不可排名**：进 `unranked`，带它的 `ReadingState` 与一行原因，
普查表照样计它。它**不会**被填成 0、NaN、`-inf` 或"最差分"。

这里刻意**没有**任何"最差"策略：一旦有，就等于把"我们不知道这个试验多好"变成"我们知道它
最差"，于是操作者读到的冠军，是因为它的对手**读不出来**才当选的。将来若真有人想要
"失败试验必须输"，那是一个新字段里的新枚举值，在 spec 层具名决定，不是这里的默认值。

### 3.5 顺序是全序且可复现

排序键 `((-value) if maximize else value, index)`。`index` 在一次运行内唯一，折叠读只保留同一
`record_id` 的最后一个事件（`_trial_id` 是 `f"trial:{run_ref}:{index:04d}"`，`:1353-1355`；
`_folded_trials` `:624-638`），所以**一次重试是一个数据点，不是两个**，顺序是全序可复现的。
并列时按更小的 `index` 在前，并列**按整个样本计数**而不是按存下来的行数计数：`ties` 列出的是
**存下来的**并列行，`tied_count` 是样本里并列的**总数**，两者在 `top_n` 截断时可以不等
（订正于 2026-09-15：早先本节写"**所有** `value == best_value` 的行都会被列出"，在
`top_n` 小于并列数时不成立，是一个会呈现唯一冠军的读法，已修，见 §12.2 第 6 条）。

**精确比较，不用容差**：两侧的浮点数来自同一份落盘 JSON，比较就是相等。
用容差会让两个不同的试验被叫做同一个冠军。

### 3.6 只排终态试验

`TERMINAL_TRIAL_STATUSES = {succeeded, failed, pruned, stopped}`（`:111`，读码）。
`pending` / `running` 没有结果：它们在普查表里计数、序号被列出，**从不被打分**。

**被剪的试验只要规则能给数就可排**——状态字符串两个方向都不决定：
`SearchTracker.run()` **无条件**写 `objective=outcome.objective`（`:1231-1242`，读码），
所以 `TrialOutcome(status="pruned", objective=1.5)` 会产生一个"被剪但有分"的记录。
（本稿纠正一句候选设计的断言："被剪的试验不可能有 objective"是错的。）

## 4. 六种读数状态（`Reading`）

```python
ReadingState = Literal["value", "no_objective", "absent", "nulled", "not_a_number", "nonfinite"]
```

| 状态 | 含义 | 来源 |
| --- | --- | --- |
| `value` | 拿到了有限浮点数 | — |
| `no_objective` | 记录字段就是 `None`（键为 `"objective"` 时） | 记录层 |
| `absent` | 这个路径在载荷里**根本不存在** | 读码 |
| `nulled` | 路径存在但值是 `null`——**这正是非有限数被 `model_dump(mode="json")` 写下去的样子** | 实测 |
| `not_a_number` | 值存在但类型不是数（字符串/布尔/列表…） | 读码 |
| `nonfinite` | 拿到的数**不是有限数**：文本形式是 `"nan"`/`"inf"`/`"-inf"` 还原而来，或者是一个 float 装不下的整数 | 实测 |

`Reading.raw` 在 `not_a_number` 时存 `repr()`，让操作者看到载荷本身而不只是一个类别名。

**`nonfinite` 的第二种来源是落地时才发现的**（§12.2 第 5 条）：`metric_value` 对任意 `int` 做
`float(current)`，而 JSON 整数没有上界，于是 `10**400` 抛 `OverflowError`。它不是"没有读数"，
而是"有一个这个模块无法比较的读数"，所以归到 `nonfinite` 而不是 `absent`；`raw` 在这种情形下
写的是**形状**（"an integer of 401 digits"）而不是 401 位数字。

**与剪枝层是细化关系，不是并列的第二套定义**。分类顺序写死，且前两级只说一次：

1. `value = metric_value(metrics, path)`。非 `None` 时，`is_nonfinite(value)` 判出 `nonfinite`
   还是 `value`——**这一级由剪枝层的函数完全决定**。
2. 否则 `reading_is_nulled(metrics, path)` 为真 → `nulled`。**同样由剪枝层的函数决定**。
3. 两级都说"没有"之后，才由本模块自己走一遍路径：走得通 → `not_a_number`（`raw` 存 `repr`），
   走不通 → `absent`。

于是"剪枝层怎么看这个读数"与本模块的状态是一一对应的，只是后面多切了一刀：
剪枝层把 `absent` 与 `not_a_number` 合并成同一个 `metric_value is None`
（它的 docstring 就是这么写的），本模块**细化了这一格**，因为它要面向操作者解释"为什么这个
试验没被排名"，而"键根本不存在"和"键在那儿但值是布尔"是两句不同的话。
`test_every_reading_state_agrees_with_the_pruning_layer`（§9 C 组；落地时从计划名
`test_the_reading_vocabulary_agrees_with_the_pruning_layer` 改名）断言的正是这条**细化关系**
本身，而不是"两边碰巧都跑了"——本仓库为"同一个概念两处定义"付过代价，这里不再付第二次。

`Reading` 的校验器：`(state == "value") == (value is not None)`，且 `value` 存在时必须有限。

## 5. 运行状态与覆盖率：五个事实、五个具名判定、绝不合并成一个 `complete`

事实全部**从台账读出**，不推断：`SearchRunRecord.status` 逐字（`:308`，读侧 `_run_records`
重新校验，`:639-653`）；`run()` 是否返回了 closing（它写的是
`closing = header if header.status == "closed" else None`，`:697`）；`header.plan["kind"]`
当作**普通字符串**；`closing/header.stats.get("exhausted")`。

### 5.1 判定表（由 `Coverage` 的校验器重算并强制）

| 条件 | verdict |
| --- | --- |
| `run_status == "unreadable"` | `unreadable` |
| `run_status == "open"` | `never_closed` |
| `run_status == "abandoned"` | `abandoned` |
| closing 在，`stats` 里**没有** `exhausted` | `unstated` |
| closing 在，`kind == "grid"`，`exhausted is True` | `walked_the_grid` |
| closing 在，`kind == "grid"`，`exhausted is False` | `budget_truncated_the_grid` |
| closing 在，`kind != "grid"`，`exhausted is True` | `drew_its_budget` |
| closing 在，`kind != "grid"`，`exhausted is False` | `stream_ended_early` |

`COVERAGE_VERDICTS` 写成**元组常量**，让"表里没有洞"这件事可以被一条测试断言，
同时 `Literal` 无法悄悄长大。

`unstated` 那一行**排在 kind 之前**：一个关掉了但 stats 里没有 `exhausted` 的网格，
必须读成"说不清"，而不是被塞进两个 grid 行里的任意一个。
（可达性读码确认：`SearchRunRecord` 的关闭校验只要求 `proposals`，`:338-343`；
`_as_stats` 同样只要求 `proposals`，`:1446-1454`。）

`stream_ended_early` 是"计划与 stats 互相矛盾"的具名桶：非网格计划却报 `exhausted=False`。
它**不**被折进上一行。**订正（2026-09-15，落地复核）**：本稿原先写着"这一格没有已知的
生产者"，**那句话是错的**。实测有两条**盘上可达**的路径，都不需要手工构造记录：

- `close_run(SamplerStats(proposals=N))` —— `SamplerStats.exhausted` 默认 `False`，
  而 `_as_stats` 对 dataclass 走 `asdict(...)`（`hyperparameter_search.py:1446-1454`），
  于是 `exhausted: False` 被**原样写进**关闭头的 `stats`；
- `close_run({"proposals": N})` —— 映射走 `dict(stats)`，**一个 `exhausted` 键都不写**。

这两条正是本表第 4 行与第 8 行的分界：**键在**（哪怕值是 `False`）走 `stream_ended_early`，
**键不在**走 `unstated`。两条用例分别钉住这两侧（可复核：

耗时也不该抄进文档——它是机器负载的函数，不是事实。）

`test_a_close_without_the_exhausted_flag_reports_unstated` 断言 `exhausted is None`、
verdict `unstated`；`test_the_default_sampler_stats_report_stream_ended_early` 断言
`exhausted is False`、verdict `stream_ended_early`）。

### 5.2 "未知"与"零"是两个字段

**实测**：一个刚 `open_run` 的头，载荷是 `status="open"`、`trial_count=0`、`stats={}`。
所以：

- 打开态的三栏在**落地实现里是两条不同的规则**，不是一条（订正于 2026-09-15 落地复核）：
  - `declared_trial_count`：`_declared_trial_count` **显式**把 `status == "open"` 映射成 `None`
    （原始字段默认是 `0`，报 `0` 会被读成"一个都没记下"：`hyperparameter_search.py:307`）。
  - `proposed` / `exhausted`：**不按状态分支**，一律从关闭头的 `stats` 读
    （`search_analysis.py::_coverage`：`stats.get("proposals")` / `stats.get("exhausted")`，
    取到非 `int` / 非 `bool` 一律归 `None`）。打开态之所以读成 `None`，是因为 `open_run`
    写的 `stats` 就是 `{}`（实测），**不是**因为代码里写了一行"open → None"。
  - **实测的后果**：往台账里追加一个 `status="open"`、`stats={"proposals": 5, "attempts": 5,
    "exhausted": True}` 的头（用 `TrialLedgerStore.append`，即公开写入接口，记录模型接受它），
    再读回来得到

    ```
    verdict: never_closed
    proposed: 5 exhausted: True declared_trial_count: None
    ```

    即：这两栏报出的是**盘上记录的事实**而不是 `None`，verdict 仍是 `never_closed`
    （判定表第 2 行先命中），`detail` 照旧说"这些计数从未被校验"。这是**记录事实优先于状态
    推断**的刻意选择，不是遗漏。复核方式：这条已经有独立用例
    `test_an_open_header_that_carries_stats_reports_them_rather_than_none`
    （`tests/autotuner/research/test_search_analysis.py:1033`），跑它即可，不必手搭——
    计划里没有这条，写测试时才发现上面的结论需要一个守卫（§12.1 D 组）。
- `status == "abandoned"` 时**不适用上面这条**：被放弃的运行，`stats` 与 `trial_count`
  **在盘上是存在的**（读码 + 本仓库自己的测试就写了 `status="abandoned"` 带 stats 与
  trial_count 的记录并读回，`tests/autotuner/research/test_hyperparameter_search.py:1737-1777`）。
  所以这两栏读**头里的实际值**（字段缺失才是 `None`），`closing_present=False`，
  verdict 是 `abandoned`，`detail` 明说"这些数**被记下来了，但从未被计数校验过**"。
  让"为打开态写 `None`"的那段话顺手盖住被放弃态，会让盘上存在的数字凭空消失。
- `unreadable` 时 `proposed` / `exhausted` / `declared_trial_count` 全部 `None`。
- **空串的含义不是一个规则，是两个**（订正于 2026-09-15 落地复核；早先本节写成"空串永远是
  '没读到'"，与模块里的字段注释矛盾）：
  - `plan_fingerprint` / `space_fingerprint`：**空串 ⇔ `sample_trust == "unreadable"`**。
    `SearchAnalysis._validate_analysis` 强制这一点（`sample_trust != "unreadable"`
    时两者必须非空），所以空串在这里确实只有"没读到"一个意思。
  - `source_config`：空串是**两种事实**共用的写法——读过了但这个运行**没有记录**源配置，
    或者根本没读到。**唯一的判别器是 `sample_trust`**，不是空串本身（模块里的字段注释写的就是
    这一点）。两者不能合并，因为"运行没记源配置"是盘上的事实，而"没读到"是关于读者的事实。

### 5.3 为什么不能合并（具体后果）

1. **`drew_its_budget` vs `walked_the_grid` 是默认情形，不是边角。** **实测**：
   出厂搜索空间只在部分参数上声明了 `grid_points`，所以
   `build_sampler(space, SearchPlan.for_grid(space))` 在**任何**预算下都抛
   `ValueError: a grid cannot enumerate ['skrl.agent.entropy_loss_scale',
   'skrl.agent.learning_rate_scheduler_kwargs.kl_threshold']: no grid_points declared for them`；
   而随机计划 `budget=3` 得到 `SamplerStats(proposals=3, attempts=9, rejected_infeasible=6,
   rejected_duplicate=0, exhausted=True)`。于是**对今天这个仓库能跑的每一次真实搜索**，
   把 `exhausted: True` 读成"空间被覆盖了"**每一次都是错的**。把它报成 `walked_the_grid`，
   等于告诉操作者"3 个点看完了，可以停止搜索了"。
2. **`budget_truncated_the_grid` vs `walked_the_grid`**：网格的计划顺序是依赖序而不是随机
   采样，所以没试到的区域与试过的区域**系统性相关**，操作者读到"网格最优"会过度自信。
   顺手可得的捷径"`proposals == budget` 就是被截断"被拒绝：预算恰好等于网格大小时
   `proposals` 也等于 `budget`。
3. **`never_closed` vs `budget_truncated`**：补救手段不同。截断靠加预算；进程被杀靠重跑，
   而且未关闭的台账里**根本没有"跑到哪了"的数**。更关键的是：未关闭运行的 argmax 是对一个
   **还不存在的总体**的断言，而那条能证明"样本就是被提议的样本"的计数不变量从未被执行。
4. **`abandoned` vs `closed`**：都让搜索停下，但只有一个的计数在读取时被校验过。
   把被放弃的运行报成完整，就是把一个未校验的计数呈现成一个已校验的计数。
5. **覆盖率 vs 结果**：`walked_the_grid` 只说网格被**走过**，不说它被**打过分**。
   所以覆盖率块永远与 `TrialCensus` 并排出现：一个完整网格如果大多数试验失败，
   它的冠军就只是唯一的幸存者——这件事在普查表里看得见，而不是被"完整"这个词暗示掉。

### 5.4 中断是它自己的事实

`running` 状态的试验（`SearchRun.interrupted_indices`，`:482-489`）计入 `TrialCensus.running`，
序号被列出；**不进** `failed`、**不进** `unranked`、**不进** `no_objective`。
"结果丢了"与"分数很低"是两件事，混在一起会同时污染这两个结论。
`pending`（已物化、训练从未开始）同样自成一项。

### 5.5 `sample_trust`：三个值，与 `error` 解耦

- `counts_checked`：`run()` 返回且 `complete` 为真——布局、哈希链、运行级检查、计数检查全跑了。
- `layout_checked`：`run()` 返回但 `complete=False`（打开/被放弃：布局与运行级检查跑了，
  计数没跑，因为没有 closing 记录）；**或** `run()` 抛了但兜底的
  `ledger.trials(run_ref=...)` 成功（覆盖运行级失败：序号断档、重复 `assignment_key`、
  计数不符——**不包括**哈希链或布局坏，那两种会一路掉到 `unreadable`）。
- `unreadable`：两次读都抛。

模型里**唯一**一条把两者绑起来的约束是 `counts_checked implies error == ""`。
`error` 除此之外与 `sample_trust` 独立——这正是降级态**可构造**的原因。
（候选设计里有一版写的是 `integrity == "unreadable" iff error != ""`，那条规则会在它自己
那条"序号断档"测试要构造的记录上抛 `ValidationError`。本稿不采纳。）

未关闭的运行**照样被描述**，只是不导出：报告列出每个已记录序号的序号、状态、逐字 objective、
以及"为什么它没被排名"。真正解决中断的试验、把运行正常关闭（`SearchTracker.close_run`）之后，
同一次调用就能导出。**刻意没有** `--allow-degraded` 之类"排名并发出可见子集"的模式。

## 6. 导出

### 6.1 两个文件，路径由调用方给

**不写台账**（§1.1）。

1. **配置**，写在 `output_path`（必填，无默认值——本仓库的规矩是模块不替一次运行发明文件
   位置，对照 `SearchTracker` 必填的 `work_root` 与 `TrialLedgerStore` 必填的 root）。
   由 `config_injection.inject_into_file(header.source_config, output_path, space,
   winner.assignment)` 写：它加载源、注入、原子落盘（staged + `os.replace`）、**读回并重验**，
   两份报告不一致就抛（`config_injection.py:448-469`，读码）。这不是图省事：它是本仓库
   **唯一**一个会校验"文件确实带上了注入"的写出路径，再写一个就是第二个需要保持同步的东西。
   YAML、引号、原子替换、读回校验**一律不重写**。
2. **回执/清单**，JSON，写在 `<output_path>.manifest.json`。内容是
   `canonical_json({"artifact": artifact.model_dump(mode="json"),
   "analysis": analysis.model_dump(mode="json")})` 加换行，先 staged 在同目录再 `os.replace`。
   它是 JSON 而不是 YAML；**不**把 `InjectionReport` 存回去再用 `model_validate` 读回来——
   `InjectedValue.changed` 是 `@computed_field`（`config_injection.py:183-194`，读码），
   往返会失败；它的完整性由 **`injection_fingerprint`**（`report.fingerprint()`，
   `hyperparameter_search.py:1088`）承担而不是"读回来还合法"，写这条的就是 `begin_trial`
   自己在 `:1084-1086` 留的注释。回执这边更简单：`SearchAnalysis` 与 `ExportArtifact`
   里**没有** `InjectedValue`，两者都是普通 JSON，所以回执可以原样 `model_validate` 读回，
   `verify_export` 也正因此不依赖任何派生字段。

**空注入实测**：`inject_assignment(source, space, {})` 抛
`ValueError: an injection must set at least one parameter`。这是 spec 层失败，从
`config_injection` 原样传出，本模块不改写。

### 6.2 一个读者一周后怎么验证"这个配置文件确实带着获胜 assignment"

四道，走四条不同的路径；前三道在 `export_best` 返回之前就跑完：

- **(a)** `inject_into_file` 自己：注入、写出、读回、重推报告，不一致就拒绝
  （`config_injection.py:463-468`）。
- **(b)** `content_hash(load_config_file(output_path)) == winner.injected_fingerprint`。
  左边是**此刻盘上**那棵树的哈希；右边是台账**自试验物化起就存着**的值——
  `begin_trial` 把同一次 `inject_into_file` 调用的结果记成 `injected_fingerprint`
  （`hyperparameter_search.py:1065`、`:1090`），而那个值由 `verify_injection` 在
  `config_injection.py:357` 算成 `content_hash(注入后树)`（`:356` 是它的孪生
  `source_fingerprint`），`:460-463` 的 `inject_into_file` 保证被哈希的是
  **从写出的文件读回来**的那棵树而不是内存里的树。
  所以这是**与一个已记录值的相等**，不是自比。回执上存成
  `expected_fingerprint` 与 `output_fingerprint` 两个数。
- **(c)** 当 `Path(winner.config_path).is_file()` 时，**逐棵比较**两棵树：
  `load_config_file(output_path) == load_config_file(winner.config_path)`。
  这是可得的最强检查——比的是产物本身而不是它的哈希，而且读者用一个 YAML 解析器、
  不需要本仓库任何代码就能跑。它**只是有时候可用**（试验工作目录是普通目录，
  没人保证它还在），所以记成 `compared_against_trial_file: bool`，并用
  `trial_config_path` 记下它去看的是哪个路径，而不是假定。
- **(d)** `verify_export(artifact)`：重读 `output_config`、重算哈希、与
  `expected_fingerprint` 比。这是**第三方**在几天后跑的那一道：两个数都在回执里、
  也就都在清单里，检查是三行 Python（`json` + `hashlib`）。

### 6.3 让导出"可信"而不只是"格式对"的那道守卫

导出**之前**，`export_best` 重算 `content_hash(load_config_file(analysis.source_config))`，
与运行头在开启时记下的 `analysis.source_config_fingerprint` 比对，不等就拒绝
（头的该字段在 `hyperparameter_search.py:1011`；`SearchTracker` 构造时甚至拒绝"盘上的文件
与传入的映射不一致"，`:930-940`）。

没有这道守卫会发生什么：操作者改了训练配置、重新导出、发布一个"与获胜试验的差异从未被
搜索探索过"的文件——**而其它每一道检查都通过**，因为它会被拿去比的指纹正是它刚刚产生的那个。
任务 4 与任务 5 都没有关掉这条路径。

### 6.4 路径解析与"不许破坏证据"

- **记录的路径按调用方给的写法解释**：`source_config`、`config_path`、`run_dir` 通常是
  **相对路径**（实测：头里存的就是传入的 `products\taili\blind_locomotion\taili_blind_config.yaml`），
  因此是相对**分析者当时的 CWD** 解析。这句话必须写在字段注释与文档里——
  一个在别的目录里跑的分析，会因为这条而拒绝导出，而原因不该靠猜。
- `output_path` 解析后**不得**等于 `source_config`（`write_injection` 已拒绝这条，
  `config_injection.py:403-406`），也不得等于 `winner.config_path`——那个文件是记录自己的
  证据，覆盖它会让检查 (c) 永远不可能。
- **已经存在的输出要被拒绝**：`output_path` 或 `<output_path>.manifest.json` 已存在时抛
  `ExportRefusedError`（具名原因）。这是对 `write_injection` 的 `os.replace` **静默覆盖**的
  一处**刻意分歧**：回执的全部价值在于"指向一个仍然可核对的配置"，覆盖掉一个旧回执指向的
  文件，就把那个回执变成了假证据。
- 父目录必须存在，本模块**不创建**。

### 6.5 `export_best` 抛什么

`ExportRefusedError`（带 `.reasons: tuple[str, ...]`）：

- `sample_trust` 不是 `counts_checked`；
- `ranked` 为空；
- 空间指纹与报告不符（`space.fingerprint() != analysis.space_fingerprint`）；
- 报告与台账矛盾（按 `trial_id` 重读的获胜记录，其 `index`/`attempt`/`assignment_key`/
  `assignment`/`objective`/**`status`** 六项逐一相等——订正：本稿原先只列了前五项，
  落地实现是六项，多出来的 `status` 让一个"分数对得上但状态被改过"的行也进不来）——
  这样一份手工拼出来的 `SearchAnalysis` 塞不进一个 assignment；
- 运行头没记源配置，或源配置漂移（§6.3），或写出文件的指纹与获胜记录的
  `injected_fingerprint` 不等；
- 获胜记录没有 `injected_fingerprint`（`failed` 是 `TrialRecord` 唯一豁免注入要求的终态，
  `hyperparameter_search.py:427-431`，读码）；
- 源配置文件不存在（把 `load_config_file` 的 `FileNotFoundError` 收成拒绝——
  "这次搜索是从哪个文件发起的已经找不到了"是**拒绝导出**，不是一次 OS 事故）；
- 源配置文件存在但**不再是合法 YAML**（`yaml.YAMLError` **不是** `ValueError`，
  订正于 2026-09-15：本稿原先把这类失败归进 `ValueError`，落地实测它直接穿透，见 §12.2 第 4 条）；
- 输出路径或回执路径会破坏证据（§6.4）——包括**回执路径等于输出路径**：回执最后写、
  经 `os.replace` 落地，所以这种路径不是撞车而是覆盖（§12.2 第 2 条）；
- 输出目录或**回执目录**不存在（§6.4 末条；回执目录原先没检查，抛的是裸 `FileNotFoundError`，
  §12.2 第 3 条）。

`ValueError`（spec 层）：`top_n < 1`、`rule.key` 为空串、`rank` 越界；
以及 `config_injection` 对"assignment 指名了空间未声明的参数"抛出的 `ValueError`，
原样传出（那是关于空间的事实，与 `begin_trial` 在同一处保持同一种切分，`:1065-1068`，读码）。

**第三类不是判决，是事故**：`OSError`（写的时候目录变成只读、盘满）以及注入器自己的
`yaml.YAMLError`。它们**不是**拒绝，因为没有人做出判断；`export_best` 的 docstring 明说这一点。
但写出配置**之后**无论抛哪一类，`_discard()` 都会先把这次调用创建的那个文件撤掉再往外抛
（§12.2 第 7 条），所以"看见异常就别猜盘上有没有半成品"这句话对三类都成立。

**两条边界检查的位置不同，这是落地时才定下来的（实测）**：

- `rank < 1` 在最前面抛（`export_best` 的第一条语句）——它与台账无关，是纯粹的调用方错误。
- `rank > len(analysis.ranked)` 的检查**排在拒绝集合之后**。顺序是规格的一部分：
  一份不可导出的报告根本没有行可数，先查上界就会报"没有第 1 行"——话是真的，
  但它把真正的原因藏起来，而且以 `ValueError` 逃出一个只捕 `ExportRefusedError` 的调用方。
  `test_the_export_refuses_a_rank_beyond_the_stored_rows`（`:1416`）的 docstring 记下了
  订正前的实测行为：顺序反了时，从一个未关闭的运行导出会抛
  `ValueError: rank 1 is outside the 0 rows`。
  （行号订正于 2026-09-15：本稿原先写的 `:1294` 是加进这一批新用例**之前**的行号，
  现在该用例在 `:1416`。）

**已知限制（写在这里而不是留给使用者发现）**：`rank` 必须在报告保存下来的名次范围内
（`1..len(analysis.ranked)`）。要导出更靠后的名次，重新 `analyze` 时把 `top_n` 调大。
`export_best` 不会为了取第 25 名而重排一遍——那会让"导出的是报告里的那一行"这件事失效。

## 7. 失败策略：读的报出来，写的拒绝掉

**这条线不是照抄 `prune_summary` 的习惯，是画在后果改变的地方。**

**为什么 `analyze()` 对台账事实不抛。** 这里的理由比剪枝层更强，而且不同：
`prune_summary` 的失败单元是**一次试验**，四个具名桶（verified / unverifiable /
unexplained / contradicted）本身就是工作产物；本模块的失败单元是**整个运行**，而报告是这个
运行**唯一**面向使用者的视图。它一抛，操作者的退路就是手工去解析 `trials.jsonl`——
那正是一周后得出错误结论的路径。先例是明写的：`trial_ledger.summary()` 的文档写着
"**Never raises**：能看一眼坏掉的台账，正是它存在的原因之一"（`trial_ledger.py:723-728`），
并保留一个具名的 `integrity_error` 字段；`prune_summary` 同样用 `error=`（`search_pruning.py:987-992`）。

**"不抛"如何不变成"不报"——机制而不是意图。** `sample_trust` 说明哪些检查跑了；
`error` 逐字携带 `"TypeName: message"`；`coverage.verdict` 说明运行状态；
普查表给每一个已记录试验留了位置并校验分项求和；`unranked` 具名列出每一个规则给不出数的
终态试验及其状态与原因；`caveats` 携带面向操作者的句子。于是一次受损的读产生一份
**每个字段都可读**的报告，而不是一个布尔值、也不是一个异常。

**为什么 `export_best()` 抛、而这并不矛盾。** 本仓库的规矩是"spec 层失败抛 `ValueError`；
运行性失败抛具名异常子类"，而"拒绝发货"是运行性的。区别在后果：**报告是被读的，配置是会被
有人拷进一次训练的文件。** 读取侧的原则（保持可读、把缺陷报出来）适用于读；
写入侧的原则（不产出你担保不了的东西）适用于写。既有代码画的是同一条线：
`write_injection` 在自己的报告解释不了那棵树时**拒绝**而不是上报
（`config_injection.py:414-421`），而 `trial_ledger.summary()` 与 `prune_summary` 是上报。
一个会返回"也许"的前置条件比一个会抛的更糟："这个配置就是获胜者跑的那个"这句话只有
两个真值，而调用方在报告之后的下一行自然就是 `export_best`——否则它还得再判断一次
"空排名到底是事实还是失败"。

## 8. 数据模型与公开 API

模块 `autotuner/research/search_analysis.py`。**八**个公开记录 + 一个内部 `_RunRead`
（不导出、不参与指纹），两个异常（`SearchAnalysisError` / `ExportRefusedError`）、
**五**个 `Literal` 词汇（`RankDirection` / `ReadingState` / `SampleTrust` / `RunStatus` /
`CoverageVerdict`）、三个公开函数。全部字段 JSON 原生（律 R4），无 `@computed_field`（R1），
无 `model_copy(update=...)`（R2），身份一律 `content_hash(model_dump(mode="json"))`（R3）。

（订正于 2026-09-15：计划写的是"六个 `Literal`"，实测是五个——`RunStatus` 与
`CoverageVerdict` 都算进去了，多算的那个从来没有过。）

```python
ANALYSIS_SCHEMA_VERSION = "rl-agent.search-analysis/v1"
EXPORT_SCHEMA_VERSION   = "rl-agent.search-export/v1"      # 回执自己的版本，与报告分开

RankDirection = Literal["maximize", "minimize"]
ReadingState  = Literal["value", "no_objective", "absent", "nulled", "not_a_number", "nonfinite"]
SampleTrust   = Literal["counts_checked", "layout_checked", "unreadable"]
COVERAGE_VERDICTS = ("unreadable", "never_closed", "abandoned", "unstated",
                     "walked_the_grid", "budget_truncated_the_grid",
                     "drew_its_budget", "stream_ended_early")
```

记录（字段略去 `ConfigDict`）：

| 记录 | 关键字段 | 说明 |
| --- | --- | --- |
| `RankingRule` | `key: str = "objective"`；`direction: RankDirection`（**无默认**） | 调用方对"什么是最好的"的回答。`fingerprint()` 走 R3，`describe()` 给出 `"objective (maximize)"` |
| `Reading` | `index, trial_id, key, state, value: float \| None, raw: str` | 一个试验在规则键上的读数。校验器：`(state == "value") == (value is not None)`，且存在时必须有限 |
| `RankedTrial` | `rank, index, trial_id, attempt, status, value, objective: float \| None, assignment, assignment_key, config_path, injected_fingerprint` | 一行排名。**同时**带排名用的数与记录自己的 objective；带足 assignment/config_path/指纹，获胜者不必再查一次 |
| `UnrankedTrial` | `index, trial_id, status, state, detail` | 规则给不出数的终态试验，**具名列出而不是丢掉**——这条记录让"5 个里的最优"与"500 个里的最优"不可能印成同一句话 |
| `TrialCensus` | `recorded, succeeded, failed, pruned, stopped, pending, running`；`terminal()` | 六项之和必须等于 `recorded`；`running` 是与 `failed` 分开的桶 |
| `Coverage` | `run_status, kind: str, closing_present, exhausted: bool \| None, budget, proposed: int \| None, declared_trial_count: int \| None, recorded, verdict, detail` | `kind` 是**普通 str**：任务 7 加第三种采样器时它被**分类**，而不是从 `analyze` 里抛一个 pydantic `ValidationError`。校验器重算 `verdict`（§5.1） |
| `SearchAnalysis` | `schema_version, run_ref, plan_fingerprint, space_fingerprint, source_config, source_config_fingerprint, space_artifact: ArtifactRef \| None, rule, rule_fingerprint, sample_trust, error, coverage, census, ranked, ranked_count, unranked, best_value, ties, tied_count, caveats`；`best()` | 整份报告。`space_artifact` 是运行头那栏的原样透出（调用方在开跑时记的，可能是 `None`），让读者能找回这次运行用的是哪份空间文件。校验器见下 |
| `ExportArtifact` | `schema_version, run_ref, rule, rule_fingerprint, trial_id, index, attempt, status, assignment, assignment_key, value, tied_count, objective, source_config, source_config_fingerprint, expected_fingerprint, output_config, output_fingerprint, compared_against_trial_file, trial_config_path, coverage_verdict, sample_trust, manifest_path`；`verified()` | 回执。**刻意没有 `verified: bool` 字段**：一个"记录存在时恒为真"的布尔不是证据，那正是本仓库被坑过的断言形状。`tied_count` 是落地后加的（§12.2 第 8 条）：拿着回执的人没有报告，而"这个配置是最优"与"有三个并列最优"是两个不同的说法 |

`SearchAnalysis` 的校验器：

1. `rule_fingerprint == rule.fingerprint()`；
2. `sample_trust == "counts_checked" implies error == ""`（**唯一**一条把两者绑起来的约束）；
3. `rank` 恰好是 `1..len(ranked)`；行按 `direction` 单调；`best_value` 就是第一行的值；
4. `ranked_count >= len(ranked)`（`top_n` 截断的是列表，不是计数）；
5. `ties` 恰好是**存下来的**并列行，`tied_count` 是样本里并列的总数，且
   `len(ties) == min(tied_count, len(ranked))`（§3.5 的订正，§12.2 第 6 条）；
6. 计数算术：`ranked_count + len(unranked) + pending + running == census.recorded`；
7. 被点名的序号（`unranked` + `pending_indices` + `running_indices`）互不重复，且每个都 `>= 1`。

   （订正于 2026-09-15：计划把第 6、7 条写成"`ranked` 与 `unranked` 的序号集合不相交，且
   与 `pending`/`running` 一起**恰好覆盖** `census.recorded`"。落地的检查是**算术**加上
   "被点名的序号不重复、下界为 1"——没有"恰好覆盖"这一条，因为台账本身可以序号断档
   （§12.2 第 1 条：断档正是这份报告要描述的形状，要求覆盖就等于要求报告在断档台账上抛异常）。
   序号集合的**上界**同样不检查，理由见 `_validate_no_trial_vanishes` 的注释。）

**函数**：

```python
def analyze(ledger: SearchLedger, run_ref: str, *, rule: RankingRule,
            top_n: int = 20) -> SearchAnalysis

def export_best(analysis: SearchAnalysis, *, ledger: SearchLedger, space: SearchSpaceSchema,
                output_path: str | os.PathLike[str], rank: int = 1,
                manifest_path: str | os.PathLike[str] | None = None) -> ExportArtifact

def verify_export(artifact: ExportArtifact) -> str      # 成功返回 "verified"
```

`analyze()` 内部顺序：`ledger.run(run_ref)` 先行（§2）；失败走兜底；再失败产出空报告，
但**仍然具名携带异常类型与消息**。`analyze()` 无时钟、无随机、无台账写入：
同一份台账 + 同一个 `run_ref` 永远得到同一个 `SearchAnalysis`（不变量 18）。
