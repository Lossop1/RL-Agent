## 1. 目标与范围

### 1.1 目标

把一次搜索的每次试验记成一条**可跨进程读回、可在崩溃后判定、可事后重放**的记录：这次选了什么
超参（嵌套 assignment）、注入到了哪个配置文件、跑在哪个目录、结果与中间观测是什么、为什么停。

任务 4 的产出是任务 5（早停剪枝）、任务 6（结果分析与最优配置导出）、任务 7（贝叶斯采样器）
的**唯一读侧入口**。它不自己跑训练、不自己决定停止、不自己排序。

### 1.2 明确不做（non-goals）

| 不做 | 理由 |
| --- | --- |
| 不实现调度器适配器 | 只规定契约（§9）。适配器要放在 `autotuner/product/`，因为它要 import `research_scheduler`，而后者反向 import 研究层（`research_scheduler.py:23-31`；`config/repository_structure.toml:131` 的注释承认二者循环）。本任务不修改任何既有文件。 |
| 不实现剪枝阈值与 patience | 属于任务 5。本任务只保证「观测槽位存在且可逐次追加、可读回」。 |
| 不做排序与「最优配置导出」 | 属于任务 6。试验记录里已带 `config_path` 与 `injected_fingerprint`，导出不需要新接口。 |
| 不扩展 `SamplerKind`、不实现贝叶斯采样 | 属于任务 7。本任务只留观测反馈协议（§8.4），并在 `SearchRunRecord.plan` 里以 dict 保存 plan，未知 kind 会**明确报错**而非静默降级。 |
| 不把搜索过程写进 `research_ledger` | 会引入「搜索结束」这一事务边界和两套哈希链错误语义；收益只是跨系统可发现性。 |
| 不修改 `research_ledger.py` 等既有模块 | 它们是已完成任务的产物；复用其**纯函数与约定**，不用它的 store（§5.1）。 |

## 3. 记录模型

### 3.1 `TrialEvent`（台账信封）

直接继承 `research_ledger.LedgerEvent`（`research_ledger.py:361-372`），只覆盖两处：

```python
class TrialEvent(LedgerEvent):
    model_config = ConfigDict(extra="forbid")           # 父类无 extra 约束
    schema_version: str = TRIAL_LEDGER_SCHEMA_VERSION   # "rl-agent.trial-ledger/v1"
```

字段沿用父类的 12 个：`schema_version / event_id / sequence / event_type / record_type /
record_id / actor / created_at / payload / payload_hash / previous_event_hash / event_hash`。
链的重算方式与 `research_ledger.py:670` 逐字一致：
`content_hash(event.model_dump(mode="json", exclude={"event_hash"}))`。

**实测**（§0.1）：继承 + `extra="forbid"` 后 JSON 回环 `event_hash` 仍相等，所以两种台账共用
一套心智模型，将来若要统一是机械操作。

### 3.2 `SearchRunRecord`（每次搜索一条）

| 字段 | 类型 | 为什么必须有 |
| --- | --- | --- |
| `id` / `created_at` / `source` / `schema_version` | 继承 `LedgerRecord` | 对齐台账约定（`research_ledger.py:44-48`）；`schema_version` 覆盖为 `"rl-agent.hyperparameter-search/v1"` |
| `run_ref` | `str` | 会话标识；由 `default_run_ref` 或调用方给出 |
| `plan` | `dict[str, Any]` | `SearchPlan.model_dump(mode="json")`。**重放的必需输入**：`replay(space, plan)` 需要完整 plan 对象，而 `plan.fingerprint()` 只是身份（`hyperparameter_sampler.py:443-450`、`:81-87`） |
| `plan_fingerprint` | `str` | 过滤与 join 键；由验证器与 `plan` 互相印证 |
| `space_fingerprint` | `str` | 与另一个空间的观测混用会让代理模型学错映射（同 `Sampler.__init__` 拒绝跨空间 plan 的理由，`hyperparameter_sampler.py:227-244`） |
| `sampling_order` | `tuple[str, ...]` | plan 的抽取顺序；指纹忽略声明顺序，重放不忽略 |
| `space_artifact` | `ArtifactRef \| None` | 复用 `research_ledger.ArtifactRef`（`id/kind/path/sha256/role/exists`）。指纹只证明「是同一个空间」，重建空间还需要空间文件路径；零硬编码下该路径由调用方传入并存档 |
| `source_config` | `str` | 出厂配置路径，由调用方传入；重放一次试验要从它重新注入 |
| `source_config_fingerprint` | `str` | `content_hash(load_config_file(source_config))`，记录「注入前长什么样」 |
| `baseline_ref` | `str` | 可选，指向 baseline 试验 id（对齐调度器 `priority=0` 的 baseline 语义，`research_scheduler.py:579`） |
| `budget` | `int \| None` | plan.budget 的冗余视图，便于读侧不经 plan 解析就筛查 |
| `max_in_flight` | `int` | 本会话最多同时在飞的试验数（§8.5） |
| `stats` | `dict[str, Any]` | `SamplerStats` 的 `asdict`。**它是区分「走完整格」与「被预算截断」的唯一依据**，且不进 plan 指纹（`hyperparameter_sampler.py:208-222`、`:191-204`） |
| `trial_count` | `int` | 关闭时写入的实际试验条数 |
| `status` | `Literal["open","closed","abandoned"]` | 运行头状态 |

不变量（`model_validator(mode="after")`，违反即 `raise`）：

- `plan_fingerprint == SearchPlan.model_validate(plan).fingerprint()`——失败即「记录里的 plan 与
  它自己声称的身份不符」。
- `status == "closed"` 时 `stats` 必须非空：不记 stats 的 closed 运行**无法自证**「网格走完了
  还是被截断了」，而 `exhausted` 正是用来回答这个的。
- `space_fingerprint`、`plan_fingerprint`、`run_ref` 非空白。
- `status == "closed"` 时 `trial_count` 必须等于 `stats["proposals"]`（否则有试验被静默吞掉，§11）。

### 3.3 `TrialRecord`（每次试验一条，可多次 supersede）

| 字段 | 类型 | 为什么事后重放需要它 |
| --- | --- | --- |
| `id` | `str` | 确定性：`f"trial:{run_ref}:{index:04d}"`。读侧按 `(record_type, record_id)` 折叠取最后一个事件（`research_ledger.py:809-813`），所以崩溃后重跑同一 index 只会 supersede，既幂等又不丢历史 |
| `run_ref` | `str` | 挂到哪次搜索 |

## 4. 四条实现铁律（每条都有实测依据，写进 code review checklist）

**R1 禁止 `@computed_field`；派生量用普通方法。**
依据：`InjectedValue` 带 `computed_field changed`（`config_injection.py:183`），含它的 `InjectionReport.model_dump(mode="json")` 回喂 `model_validate` 因 `extra="forbid"` 抛 `ValidationError`（本次实测：装 7 条取值的报告报 `7 validation errors for InjectionReport`，逐条为 `values.N.changed`）。台账的读回路径必然要求可再校验，因此记录模型一律用「存储字段 + `model_validator` 自洽校验」。
（普通 `@property` 在 pydantic v2 上的行为本次未验证，故 `duration_s` 用**普通方法**实现，不进 `model_dump`。）

**R2 禁止 `model_copy(update=...)`。**
依据：pydantic v2 的 `model_copy` 不跑任何 validator（第 1 名评审实测定性：`M(a=0).model_copy(update={"a":5})` 返回 `a=5, b=""` 不报错，而 `M(a=5)` 抛 `ValidationError`）。所有状态跃迁必须走：

```python
def _supersede(self, prev: TrialRecord, **changes: Any) -> TrialRecord:
    payload = {**prev.model_dump(mode="json"), **changes}
    return TrialRecord.model_validate(payload)      # 重跑全部不变量
```

**R3 哈希一律对 `model_dump(mode="json")` 的结果算，且入台账前先转 dump。**
依据：`content_hash(model)`（走 `_dump`，带 `exclude_none`）与 `content_hash(model.model_dump(mode="json"))` 结果不同（第 2 名探针 2 实测）；写法一律 `content_hash(record.model_dump(mode="json"))`。`TrialLedgerStore.append` 内做转换，绝不把 BaseModel 交给任何 `_dump`。

**R4 记录字段必须全是 JSON 原生类型；禁止把 BaseModel 塞进裸 dict 再喂 `content_hash`。**
依据：`content_hash({'x': M()})` 抛 `TypeError: Object of type M is not JSON serializable`（调查事实实测）。嵌套模型只在 `model_dump(mode="json")` 之后才允许出现；`InjectionReport` 一律当**不透明 JSON** 存，永不 `model_validate` 回 `InjectionReport`。

## 5. 台账存储：`TrialLedgerStore`

### 5.1 为什么不复用 `ResearchLedgerStore`（三条，前两条决定性）

1. **正确性**：它的锁是进程内 `threading.Lock`（`research_ledger.py:603`），`append` 是「读全量 → `sequence=len+1` → 追加」（`:641-642`、`:656-676`）。两个进程并发 append 会写出重复 sequence，此后**任何读取永久抛 `ledger.sequence_gap`**（`:619-620`）。搜索天然会产生并发写入形态。
2. **成本**：每 append 一次全量重读 + 全量哈希，O(N²)。第 1 名实测 100/200/400 次 append = 1.455s / 3.526s / 9.351s（其评审独立复现 100/200 次 = 1.481s/3.537s）。
3. **耦合**：复用需要往 `RECORD_MODELS`（`:382-403`）加键、往 `validate_record` 的 if 链（`:419-497`）加分支，等于修改一个已完成任务的共享模块；且与 20 种研究记录共用单一 `events.jsonl`（`:607`）。

复用的是它的纯函数与约定（§8.1），不是它的 store。

### 5.2 append 的三条机制

**机制 1：O(1) 尾读。**
在跨进程锁内，从文件尾部倒读最多 `tail_window_bytes`（默认 8 KiB，不足则倍增窗口直到找到 `\n` 或读完整文件），取**最后一条完整事件**：

- 校验该行可 `json.loads` → 否则抛 `TrialLedgerIntegrityError("bad_json", ...)`；
- 校验该行自洽：`event_hash == content_hash(dump minus event_hash)` → 否则抛 `TrialLedgerIntegrityError("hash_mismatch", ...)`（这一次 sha256 是便宜的，用来堵住「基于损坏的尾写入链」）；
- `sequence = last.sequence + 1`，`previous_event_hash = last.event_hash`；
- `open("a", newline="\n")` 写 `canonical_json(event) + "\n"`，`flush` + `os.fsync`。

链的**全量**校验只在读侧 `events(verify=True)` 做（与 `research_ledger.py:614-627` 的三项检查同款）。

**机制 2：跨进程锁。**
`<root>/.write.lock` 以 `os.open(path, os.O_CREAT | os.O_RDWR | (os.O_BINARY if os.name == "nt" else 0))` 打开（`trial_ledger.py:92`），再对该 fd 的**第 0 字节取记录锁**：POSIX 下 `fcntl.flock(LOCK_EX | LOCK_NB)`，Windows 上 `msvcrt.locking(LK_NBLCK, 1)`（`_try_lock`，`trial_ledger.py:189-211`）。取到即持锁；取不到则每 `0.02s`（`_LOCK_POLL_S`，`:103`）重试，超过 `lock_timeout_s=5`（`DEFAULT_LOCK_TIMEOUT_S`，`:107`）抛 `lock_timeout`，消息里带上锁文件记的持有者身份（`pid` 与取锁时间；纯诊断，没有任何判断读它的内容）。**释放就是关闭 fd**（`:333`），进程被杀也由内核释放（POSIX 实测：持锁者被 SIGKILL 后 0.001s 即可重新获取；Windows 上 TerminateProcess 同理）。临界区只覆盖「读尾 + 追加 + fsync」，绝不跨训练。

**锁文件不再删除，也没有 stale 判定**：`DEFAULT_STALE_LOCK_S` 随旧协议一并删除，锁文件创建一次、长期存在。旧协议（`O_CREAT | O_EXCL` 建文件即持锁、用完 `unlink` 释放）在本仓库仍见于 `research_state.py:202-228` 与 `research_supervisor.py:68-92`，本模块**有意不照抄**：unlink 释放与等待者建文件会交错（等待者刚建好的锁可能被离开者删掉，第二个写者就进去了），而崩溃的持有者只能靠文件年龄猜，分不清「还活着」与「崩溃留下的」。`research_scheduler.py` 没有任何文件锁，只有进程内 `threading.RLock`（`:133`/`:261`/`:505`/`:522`），不是这套协议的任何一处来源。两种原语**对同进程的两个句柄同样互斥**（实测：同进程第二个 fd 在字节 0 上取锁被拒），因此不再叠一层 `threading.Lock`。

**机制 3：撕裂尾行自愈。**
`append` 在锁内先 `trim_incomplete_tail()`：若文件不以 `\n` 结尾，截断到最后一个 `\n`，返回丢弃字节数。读侧对「最后一个 `\n` 之后的字节」一律不算事件（`events()` 抛 `torn_tail` 而不是把半个 JSON 行喂给 `json.loads`）。判定必须显式用 `raw.endswith("\n")`：实测完整行 `endswith("\n") is True`、撕裂行 `False`，而两者 `len(splitlines())` 都是 1，行数区分不了（第 1 名原稿此处数值写错，已按评审复核值修正）。

### 5.3 文件与位置

| 项 | 值 | 归属 |
| --- | --- | --- |
| 事件文件 | `<ledger_root>/trials.jsonl` | `ledger_root` 调用方传入，**无默认值** |
| 锁文件 | `<ledger_root>/.write.lock` | 模块常量 |
| 试验目录根 | `<work_root>/trials/<trial-{index:04d}-a{attempt}-{token}>/` | `work_root` 调用方传入，**无默认值** |

**文件名是 `trials.jsonl` 而不是 `events.jsonl`**：`research_ledger.py:605-607` 已占用 `events.jsonl`，同名会让调用方误指向研究台账目录时两种事件写进同一文件、互相破坏哈希链。

**root 必填、无默认值**：`research_ledger` 的类默认 `output/research/ledger`（`:605`）与 CLI 默认 `output/research_ledger`（`:833`）已互相矛盾，这是「默认路径会悄悄造出第二份台账」的现成教训。

**一个 root 恰好承载一次搜索**（采纳第 2 名的契约）：读侧强制「第一行必须是 `run`、其后不得再出现 `run`」，把「两次搜索混进一个 root」变成硬错误。

```
│     │              error=f"{type(e).__name__}: {e}", finished_at=time.time()),
│     │          event_type="supersede")
│     │      raise                                       # 先记，再抛（§6.3(b)）
│     ├─ 校验 outcome.status in TERMINAL_TRIAL_STATUSES，否则 raise SearchError
│     └─ store.append("search_trial",
│            _supersede(rec,
│                status=outcome.status,
│                objective=outcome.objective,
│                metrics=dict(outcome.metrics),
│                observations=tuple(outcome.observations),
│                stop_reason=outcome.message if outcome.status in {"pruned","stopped"} else "",
│                error=outcome.message if outcome.status == "failed" else "",
│                backend_ref=outcome.backend_ref, log_path=outcome.log_path,
│                finished_at=time.time()),
│            event_type="supersede")
│
├─ 5. self.close_run(stats=sampler.stats)               # :153-167，幂等
└─ 6. return self.read()                                # 落盘后再从磁盘读回
```

### 6.1 为什么每条试验 3 次写

`pending`（目录与配置已就绪、未启动）→ `running`（`runner.run` 调用前）→ 终局。三态在崩溃取证上各自可判：`pending` 有记录但无 `running` 说明「物化完成但训练从未开始」；`running` 说明「训练确实启动过」。每次 append 是 O(1) + 一次 `fsync`，对几百条量级的搜索可接受；写放大问题记入 §11.2。

### 6.2 为什么 `run()` 以 `read()` 收尾（嫁接 A）

落盘后再从磁盘解析回来，等于每次运行都顺带跑一遍完整性校验（§7.2），并把 `read()` 的返回作为 `run()` 的返回值。写盘格式与读取格式一旦漂移，第一次运行就暴露，而不是等任务 6 分析时才发现。

### 6.3 三个刻意的失败处置

（a）**`preflight` 失败：零副作用、同步抛错。**
不写任何记录、不建目录、不提交作业，`SearchPreflightError` 直接冒泡。若写成「记录失败再继续」，一次全局误配置（例如缺 `mechanisms.json`）会把每条试验都写成 failed 然后「搜索完成」，这是最恶劣的静默失败。适配器要做的四项检查见 §9。

（b）**物化/执行失败：先记再抛。**
构造 `TrialRecord` 之后的任何异常（注入失败、`runner.run` 抛异常、`outcome.status` 非法）都先写一条 `failed` 记录（原因、时间戳齐备），再把异常抛给调用方。反例是 `research_scheduler.py:676-681` 的 `except Exception: release + status=FAILED`（吞掉异常，调用方永远看不到 `FileNotFoundError`）与 `_schedule_loop` 的 `try/except` 后 `print`（`:638-641`）。兼取两端：记录能解释失败，异常保证可见。

（c）**不静默跳过。**
任何一条试验失败都会中止本次 `run()`（run 保持 `open`，`complete is False`）。调用方修好问题后用同一 `run_ref` 重跑：已终局的 index 被跳过（不重复消耗资源），但跳过是**可见的**——盘上有那条 failed 记录。需要显式重试某个 index 时传 `retry=(index,)`，`attempt` 递增、历史保留。

## 7. 持久化、位置与崩溃后可恢复性

### 7.1 行格式

`<ledger_root>/trials.jsonl`，一行一个 JSON 事件，行序恒为：1 行 `search_run` → N 行 `search_trial`（每行一个 supersede 事件）→ 最多 1 行 `search_run` 的关闭事件。

```json
{"actor":"search_tracker","created_at":"2026-09-14T09:00:00+00:00",
 "event_hash":"...","event_id":"event:...","event_type":"supersede",
 "payload":{"id":"trial:search:abc:0003","run_ref":"search:abc","index":3,"attempt":1,
            "objective":0.812,"metrics":{...},"status":"succeeded",...},
 "payload_hash":"...","previous_event_hash":"...",
 "record_id":"trial:search:abc:0003","record_type":"search_trial",
 "schema_version":"rl-agent.trial-ledger/v1","sequence":7}
```

`created_at` 用 `research_ledger.utc_now()`（ISO 串，`:26-27`）；`started_at`/`finished_at` 用 epoch 浮点（对齐 `BackendHandle.started_at: float`，`research_supervisor.py:169-171`），因为秒级 ISO 会把短试验的时长压成 0 或 1。

### 7.2 读回校验（`SearchLedger` 在返回前逐条执行，任一项不符抛 `TrialLedgerIntegrityError` / `SearchIntegrityError`）

| # | 检查 | 抓住的失败 |
| --- | --- | --- |
| 1 | 每行必须是完整合法 JSON（尾行必须以 `\n` 结尾） | 崩溃写出的半行、被截断的文件 |
| 2 | 至少一行且第一行 `record_type == "search_run"` | 空台账 / 布局错 |
| 3 | 其后不得再出现 `record_type == "search_run"` | 两个搜索被写进一个 root |
| 4 | `sequence` 从 1 连续递增 | **中间丢了一条事件** |
| 5 | 每行 `previous_event_hash` == 上一行 `event_hash` | 行被删除/重排/插队 |
| 6 | `event_hash == content_hash(body minus event_hash)` | 行被篡改 |
| 7 | trial 的 `index` 严格 1..N 且 `assignment_key` 无重复 | 同一试验被记录两次 |
| 8 | 关闭时 `closing.trial_count == closing.stats["proposals"] == len(trials)` | **采样器提议了 N 条，落盘只有 M<N 条**（「没有静默截断」的主锚点） |
| 9 | `header.plan_fingerprint == SearchPlan.model_validate(header.plan).fingerprint()` | 记录里的 plan 被改过或与指纹不符 |
| 10 | `search_run` 的关闭事件至多一行 | 重复关闭（第 2 名缺陷 2） |
| 11 | 关闭事件之后不得再出现 `search_trial` 事件 | 关闭后仍在追加（同上） |
| 12 | 每条 trial 记录的 `plan_fingerprint`/`space_fingerprint` == header 的同名值 | 跨空间的记录混入 |

第 8 条的两个数字由**不同代码路径**产生：`closing.trial_count` 取自 `len(run.trials)`，`closing.stats["proposals"]` 取自 `SamplerStats.proposals`（字段在 `hyperparameter_sampler.py:208-222`，自增在 `:253-256`，每 yield 一条）。同一条不变量在**写侧**（`close_run` 直接 raise）与**读侧**（第 8 条）各检查一次，与 `write_injection` 重算哈希（`config_injection.py:414-421`）、`inject_into_file` 比对读写两份报告（`:464-468`）是同一手法。

`SearchRun.complete := closing is not None`。**未关闭即是未完成**——崩在中途的运行不会留下「看起来完成的搜索」。

### 7.3 崩溃后可恢复性的六条机制

1. **追加即持久**：每个事件 `write` 后 `flush` + `os.fsync`，进程崩溃最多丢掉「正在写的那一行」。
2. **撕裂尾行自愈**：下次 append 在锁内截断最后一个 `\n` 之后的残字节；`summary()["incomplete_tail_bytes"]` 可观测。
3. **记录级折叠 + 确定性 id**：`TrialRecord.id = f"trial:{run_ref}:{index:04d}"`，读侧按 `(record_type, record_id)` 取最后一个事件（同 `research_ledger.py:809-813` 的折叠语义）。`run_ref` 默认确定性派生（§3.4），所以重跑同一 index 是 supersede，不是重复。
4. **幂等的 run 边界**：`open_run`/`close_run` 按 `run_ref` 幂等——已存在且指纹相同即复用，不追加；指纹不同即抛错。这把「崩溃后重连」变成无需新机制的常规路径。
5. **唯一的试验目录名**：`trial-{index:04d}-a{attempt}-{token}`，`token = uuid4().hex[:8]`。被 kill -9 打断后重跑同一 index 会用新目录，永不撞 `FileExistsError`（第 2 名原稿用确定性目录名 + `exist_ok=False` 会撞）。遗留的孤儿目录由 `SearchLedger.orphan_dirs()` 列出（扫 `<work_root>/trials/` 下未被任何记录引用的目录），作为诊断而不是自动清理。
6. **哈希链**：`events(verify=True)` 逐行校验，手改一行即被抓住。

**崩溃留下的可判定状态**：

| 盘上状态 | 判定 | 默认处置 |
| --- | --- | --- |
| 有 `pending` 记录、无后续 | 物化完成但训练未启动 | 重跑，`attempt+1` |
| 有 `running` 记录、无终局 | 进程死于该试验中途 | 计入 `interrupted_indices()`；`retry_interrupted=False` 时不重跑，`True` 时 `attempt+1` 重跑 |
| 无记录 | 还没跑到 | 正常执行 |
| 有 failed 记录 | 显式失败 | 跳过；要重试则传 `retry=(index,)` |
| 孤儿目录 | 崩溃发生在「mkdir 之后、append 之前」的极窄窗口 | `orphan_dirs()` 报告 |

需要强调的边界：一条处于 `running` 的试验若本进程被 kill，结果永久丢失，**不猜测**——不允许从 `training.log` 反推结果（那是猜测，不是记录）。

### 7.4 一个已知的并发边界（未决）

两个进程同时用同一 `run_ref` 恢复同一 `ledger_root`：文件锁把 append 串行化，但两边都会重新执行同一 index（目录名唯一，所以不会撞目录，只会写两条记录（后者 supersede），并且真的会跑两次训练）。本设计**不提供 writer 租约**。缓解：约定单一 writer 进程；真要防，需要复用 `ResourceLeaseStore` 的 lease 语义（`research_supervisor.py:68-92`），列为任务 4 之外的决定。

### 8.5 嫁接 C：`history_len` 与 `max_in_flight`

- `SearchRunRecord.max_in_flight`：本会话最多同时在飞的试验数，由调用方给（默认 1）。
- `TrialRecord.history_len`：选这条 assignment 时，已存在几条 `is_observation()` 为真的试验。
- 可判定语义：**第 i 条 assignment 是在看到 `history_len` 条观测之后选出的**。非自适应采样器（grid/random）的序列与观测无关，`history_len` 仍如实记录；自适应采样器只有 `max_in_flight == 1` 时才满足「每条都看到了它前面所有结果」，否则等价于批采样。这个判据事后可从台账复原，而不是只活在命令行里。

## 9. 产品层调度器适配器契约（本任务不实现，只规定）

适配器应放 `autotuner/product/`（research 不 import `research_scheduler`：它反向 import 研究层，`research_scheduler.py:23-31`，而 `config/repository_structure.toml:131` 注释承认二者循环）。契约：

```python
class SchedulerTrialRunner:            # 实现 autotuner.research.hyperparameter_search.TrialRunner
    def __init__(self, *, scheduler: ResearchScheduler, mechanism_artifact: Path,
                 resources: Sequence[str], command: Sequence[str],
                 work_root: Path, max_seconds: float | None = None) -> None: ...

    def preflight(self, request: TrialRequest) -> None:
        # 必须在花掉任何 GPU 之前完成，全部抛带路径/键名的异常，禁止吞异常：
        # (1) mechanism_artifact / "mechanisms.json" 必须是文件
        #     —— 调度器把同一检查放在调度线程里（research_scheduler.py:413-415），
        #        异常被 _try_start_next 的 except Exception 吞成异步 FAILED（:676-681）
        # (2) resources 非空，且 len(resources) <= scheduler.gpu_pool.get_stats()["total"]
        #     （get_stats: :244-253；分配是 timeout=0.0 非阻塞 :665，要不到卡的作业
        #      会反复放回队首并挡住后面所有作业 :650-660、:667-671）
        # (3) command 非空且全为 str（对齐 research_supervisor.py:204-209 的 argv 校验）
        # (4) max_seconds 与 resource_budget 的键名由调用方给出，适配器不造默认值
        #     （调度器的 3600.0 默认值硬编码在 :728，不要复制）

    def run(self, request: TrialRequest) -> TrialOutcome:
        # 1. 把 mechanism_artifact 拷成 request.workspace/candidate（对齐 _copy_candidate
        #    的布局 :362-375，使 workspace/candidate/mechanisms.json 存在）
        # 2. 用调用方给的 command 造 ExperimentPlan（training_window["command"] 必须是
        #    argv 列表；request.config_path 是绝对路径，直接作为 argv 的一项传入，
        #    不需要任何命令模板占位符约定）
        # 3. job_id = scheduler.submit_experiment(plan, candidate_dir)
        # 4. 轮询 get_job_status(:772-787)，读 job.execution_result(:79，只在此刻读一次并拷出)
        #    COMPLETED → objective/metrics 由调用方注入的 ObjectiveExtractor 从
        #                execution.evaluation 提取；FAILED → message = job.error_message
        # 5. 返回 TrialOutcome(...)；超时/取消路径暴露 CancellableTrialRunner.cancel
```

### 11.2 真实存在的风险（接受或缓解）

1. **append 不校验全链**：O(1) 尾读意味着「只校验尾行自洽」，历史链的全量校验只在读侧。若尾行被篡改且恰好自洽（不可能在不重算的情况下发生，因为 `event_hash` 是内容哈希），写入会基于它。缓解：尾行自洽校验（一次 sha256）+ 读侧全链校验。取舍明确。
2. **写放大**：每条试验 3 次 append × 一次 `fsync`。几百条量级可接受；千级以上需要批量 append（一次 `fsync` 多行）。**未实现**，记为后续优化项，且接口不变（只改 `TrialLedgerStore` 内部与新增一个 `append_many`）。
3. **`fsync` 与跨进程锁在 NTFS 上的实际成本/语义**：设计稿写的是沿用 `research_state.py:202-228` 的 `O_CREAT|O_EXCL` 模式，实现**没有沿用**（原因见 §5.2 机制 2），因此这一条的原文与代码不符，已按实测改写。实测：本地 NTFS 上「两个真子进程各写 25 条」有用例并稳定通过（`test_two_processes_appending_do_not_produce_duplicate_sequences`）；记录锁的四条性质——同进程两个句柄互斥、读被锁字节被拒（对持有者本人的第二个句柄同样如此）、进程被杀后由内核释放、锁路径不可用时立刻报错——都有用例或探针实测（§5.2、§11.4）。设计稿声称的「`O_CREAT|O_EXCL` 在锁文件已存在时抛 `PermissionError`(EACCES) 而非 `FileExistsError`」**在本机不成立**：对已存在的文件 `os.open(p, O_CREAT|O_EXCL|O_WRONLY)` 抛的是 `FileExistsError` errno 17，即使该文件正被另一个句柄打开也一样。仍未验证：多进程 append 的**耗时**（只有"不重读全文件"的结构性用例 `test_append_does_not_reread_the_whole_file`，没有计时）、网络文件系统上的记录锁语义（`_write_lock` 的 docstring 记着本仓库没有在那种文件系统上跑过）。
4. **无 writer 租约**：§7.4。两进程同时恢复会重复执行同一 index。
5. **`objective` 的权威来源仍未定**（调查事实的 unknown）：本设计把它做成 runner 的输入，任务 4 不推导。代价是任务 6 的「最优」定义仍悬在调用方一侧。
6. **`_jobs` 无上界与评估持锁**（调度器侧）：由适配器承担，见 §9。
7. **`REPLAYABLE_SAMPLER_KINDS` 与 `SamplerKind` 的耦合**：靠 A23 的测试强制同步；忘记同步的方向 fail-safe。
8. **pydantic `@property` 行为未验证**：故派生量用普通方法（R1），代价是不能写 `rec.duration_s`（须 `rec.duration_s()`）。

### 11.3 需要人拍板的未决问题

1. **规范目录**：`ledger_root` 与 `work_root` 由调用方给，但团队认定的规范目录是什么？`research_ledger` 的类默认与 CLI 默认已互相矛盾（`:605` vs `:833`），不拍板会在同一仓库里出现两份搜索台账。
2. **是否需要跨进程并发写**：本设计按「需要」来防（跨进程锁），实际代价是 `_try_lock` + `_write_lock` 里那几十行；实现**没有** stale 锁策略（旧协议的年龄判定已随记录锁删除，见 §5.2 机制 2）。若确定单 writer，这部分可以砍掉而读侧校验不受影响。
3. **是否要把「整次搜索的 outcome」写进 `research_ledger`**：本设计列为 non-goal（一次搜索一条、不是一次试验一条），理由是它会引入「搜索结束」这一事务边界与两套哈希链错误语义；收益只是跨系统可发现性。
4. **`max_seconds` 的默认**：本设计一律由调用方给、`None` 表示不限，绝不复制调度器硬编码的 `3600.0`（`research_scheduler.py:728`）。若团队要求默认值，需明确放在哪一层。
5. **`retry_interrupted` 的默认语义**：默认 `False`（报未完成，不自动重跑）。若产品侧希望「重启即自动续跑」，需要显式改为 `True` 并在调用点记录这一策略。

### 11.4 未验证清单（诚实列出）

- `TrialEvent` 继承 `LedgerEvent` + `extra="forbid"` 后 JSON 回环 `event_hash` 仍相等：第 1 名 §10.5 声称实测为真，**本次合成未重跑**。A11 是第一步就要跑的探针。
