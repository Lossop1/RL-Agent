## 1. 目标与范围

在一条搜索试验还在跑的时候，从训练进程已经产出的逐步指标流里判断"这个试验没戏"，把它停掉，
并在任务 4 的台账上留下一条可读、可复核的判定记录。

成败以下列三条为准：

1. **判定的核心是纯函数**——给定一条曲线（`TrialObservation` 序列）返回一个判定或 `None`，
   不读文件、不看时钟、不起线程。所有 I/O 与并发都在注入的接缝后面。
   于是策略部分可以用手写曲线完全离线验证，不需要训练、GPU 或网络。
2. **判定落在任务 4 已提交的写侧门面上**（`SearchTracker.observe` / `SearchTracker.finish`），
   **不改动任务 4 的任何一个文件**。
3. **判定可复核**：台账上留下的判定记录能被第三方仅凭台账重算出来，或者被明确标记为"不可复核"，
   而不是写一个无法追溯的状态字符串。

关于剪枝的代价，必须说清楚：**剪枝只省墙上时间**。`plan.budget` 是采样器提案数的上界，
剪掉一个试验不释放预算（写侧检查 `hyperparameter_search.py:1326`，读侧 `_check_counts:706-726`）。
一个被剪的试验仍然占用它的槽位，`trial_count == stats.proposals` 的不变量照旧成立。

STOP_REASON_PREFIX = "prune:"
PruneReason = Literal["nan_metric", "metric_floor", "metric_stall"]


def metric_value(metrics: Mapping[str, Any], path: str) -> float | None:
    """按点分路径取一个数值。

    缺失 / 类型不对 / 布尔量 → None。
    字符串 "nan"/"inf"/"-inf"/"NaN"/"Infinity" 会被**还原成** float('nan')/inf —— 这不是宽容，
    而是必需的：台账的落盘路径是 model_dump(mode="json")（trial_ledger.py:565），它把
    float('nan') 写成 null（本轮实测，pydantic 2.12.5：{'total': nan, 'inf': inf} →
    {'total': None, 'inf': None}，字符串 "NaN" 幸存），所以非有限读数必须在**写入曲线之前**
    规范化成字符串才能穿过台账。

    "取不到"（None）与"取到 NaN"（nan）是两件事：NaNRule 只认后者。
    """


def is_nonfinite(value: float | None) -> bool:
    """value 是 float 且不是有限数。None 返回 False（缺失不是 NaN）。"""


def canonical_metric(value: float | None) -> float | str | None:
    """写进台账前的规范形式：有限数 → float；非有限 → 'nan'/'inf'/'-inf'；None → None。

    metric_value 是它的逆。这一对函数是"曲线能穿过台账再被读回来"的承重墙。
    """

### 3.2 纯核心：规则

```python
class _RuleBase(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)
    kind: str
    at_step: int | None = None              # 绝对步数门控
    at_total_fraction: float | None = None  # 总步数比例门控

    # 门控**恰好一个**：两个都给是"两个真值来源"，都不给是"这条规则在哪个时刻生效没有写下来"，
    # 两种都 raise ValueError。比例门控在曲线里没有 total_steps 时返回 None（不猜分母）。


class NaNRule(_RuleBase):        # kind="nan_metric"
    metric: str
    # 自门控步起，曲线上任意一点该指标非有限即判死。唯一带"历史记忆"的规则，
    # 所以它需要看到完整曲线，固定窗口缓存对它无效。


class FloorRule(_RuleBase):      # kind="metric_floor"
    metric: str
    threshold: float
    mode: Literal["floor", "ceiling"] = "floor"
    patience: int = 1
    # 连续 patience 个观测跌破(floor)/超过(ceiling)阈值即判死。
    # 取不到值或非有限的观测既不计入、也不打断连续段（NaN 归 NaNRule 管）。


class StallRule(_RuleBase):      # kind="metric_stall"
    metric: str
    min_delta: float
    window: int
    # 最近 window 个观测的 max-min <= min_delta 即判死（泛化的"平台期"）。


PruningRule = Annotated[NaNRule | FloorRule | StallRule, Field(discriminator="kind")]
```

取证读数刻意分成两条路：`NaNRule` **不**把非有限数写进判定（`observed=None`），只把原因写进 `detail`；
`FloorRule` / `StallRule` 只会拿到有限值，直接把值存进 `observed`。

### 3.3 纯核心：判定与停止原因

```python
class PruneVerdict(BaseModel):
    """一条"这个试验没戏"的判定。

    stop_reason 是**存储字段**而不是 @computed_field —— 任务 4 的法则要求记录能原样走完
    model_dump(mode="json") → model_validate，计算字段做不到（先例：SearchRun.complete，
    hyperparameter_search.py:474-480，同样是"存储 + 校验器保持同步"）。
    """

    model_config = ConfigDict(extra="forbid", frozen=True)
    reason: PruneReason
    step: int                          # 判定所依据的观测步
    metric: str
    observed: float | None = None      # 恒为有限值或 None；NaN/inf 绝不进这里
    threshold: float | None = None
    detail: str
    stop_reason: str                   # 必须等于 format_stop_reason(reason, step, detail)

    # 校验器：step >= 0；detail 非空；observed/threshold 若给出必须有限；
    # stop_reason 必须带 STOP_REASON_PREFIX，且必须与自身的 reason/step/detail 自洽
    # （防止台账里出现一条读起来像另一个决定的 reason）。


def format_stop_reason(reason: PruneReason, step: int, detail: str) -> str:
    return f"{STOP_REASON_PREFIX}{reason}@{step} {detail}"


class PruneStopReason(BaseModel):
    model_config = ConfigDict(extra="forbid", frozen=True)
    reason: PruneReason
    step: int
    detail: str


def read_prune_stop_reason(text: str) -> PruneStopReason | None:
    """台账的 stop_reason → PruneStopReason；不是本模块写的形状 → None。"""
```

`stop_reason` 的线上格式是本模块**单方面提出**的契约：今天没有任何外部消费者（见 §6）。

**R-3 `at_total_fraction` 在真实部署里可能是死的。**
`blind_tp_env.py:3103` 读 `TAILI_TOTAL_STEPS`（默认 `"0"`）。本轮**实测**：
`output/current_balanced_telemetry.jsonl` 全部 4583 行的 `total_steps` 都是 `null`，

**R-4 非有限读数穿过台账会变成 `None`（本轮实测，pydantic 2.12.5）。**
`float('nan')` / `float('inf')` 经 `model_dump(mode="json")` → `None`（字符串 `"NaN"` 幸存）。
而 `TrialLedgerStore.append` 的落盘正是 `model_dump(mode="json")`（`trial_ledger.py:565`），
`canonical_json` 又走 `model_dump(mode="json", exclude_none=True)`（`research_ledger.py:30-37`）。
后果：若把原始 `float('nan')` 交给 `observe()`，台账里那条曲线读数变成 `None`，
`NaNRule` 再读时**不点火**，"仅凭台账重算"因此失败——一条 NaN 剪枝会变成永久不可复核的记录。

- 选项 A（本文默认）：解析器与 sink 在写入前用 `canonical_metric` 把非有限值写成字符串
  `"nan"/"inf"/"-inf"`，`metric_value` 负责还原。后果：曲线穿过台账后仍可重算；
  代价是多一个规范化步骤，绕过 sink 的调用方会破坏它（由 `verify_decision` 的豁免路径显式识别）。
- 选项 B：判定不在曲线里存读数，只在 `PruneDecisionRecord.observed` 里存规范字符串。
  后果：审计时"重算"退化成"读取记录"，不再是第三方重算。

**R-9 参考曲线源的开销。** 把整条曲线放在内存里、每次轮询对全前缀重判（O(n)）——
这部分与实现无关，是策略接口（每轮拿完整曲线）带来的。**读取侧的开销分两条分支，必须分开说**：
JSONL 分支按字节续读，每次只读新字节；文本日志分支每次调用整文件重读（O(file)），
轮询间隔越短这个代价越明显。参考实现可接受；**不**用固定窗口缓存，
因为一步 NaN 会在很久以后被遗忘，而 `NaNRule` 依赖看到完整曲线。

点数速率的**实测**（本稿此前写的是"默认约 10 秒一点 → 10 小时约 3600 点"，两处都错）：
`output/current_balanced_telemetry.jsonl` 共 4583 行，首末 `ts` 跨 **7105.5 秒**，
得 **1.551 秒/点**、**恰好 10.0 步/点**。发射间隔是**按步**计的
（`blind_tp_env.py:3102` 的 `TAILI_TELEMETRY_INTERVAL` 默认 10，判定是
`self._rew_log_step % telemetry_interval == 0`），所以"10 秒一点"把步当成了秒。
按实测速率，10 小时约 **2.3 万点**，是原稿数字的约 6.4 倍；O(n) 前缀重判在这一量级上
仍可接受（每轮对 2.3 万点做一次遍历），但原稿低估了它的成本。

**R-10 分层。** 新模块不得 import `autotuner.locomotion_console` / `products` / `autotuner.training` /
`autotuner.adapter`（`config/repository_structure.toml:54-62`）；允许的研究层 import 是

### 实现阶段的实测发现（运行出来的，不是读出来的）

把本设计写成代码时**跑**出来的六条。设计稿此前没有它们，其中三处改动了公开接口。

1. **台账布局陷阱是真的，且比评审所说更严重**——本轮最重要的一条。
   实测：向一个空白搜索台账先写一条 `prune_policy` 记录，之后 `SearchLedger(store).runs()`
   抛 `TrialLedgerIntegrityError: unknown_layout`。`_validate_layout`
   （`hyperparameter_search.py:574-622`，`unknown_layout` 抛在 `:587/:592/:597/:609`）
   对**任何**首个事件不是 `search_run` append 的非空台账都抛，连 `open_run`
   自己也读不了。代价不是一个记录，是整个根**永久**不可读；`_require_open` 的文档字符串
   （`:1487-1490`）早已写明这一点，但设计稿只把它当成一句提醒。
   **所以接口改了**：新增 `store_policy_record(store, policy, *, precondition, ...)`，
   且 `precondition` **故意不给默认值**——危险的那种写法必须显式写出来；
   `TrackerPruningSink` 写策略记录时传 `tracker._require_open`。
   用例：`test_a_record_written_before_the_run_header_makes_the_ledger_unreadable`
   （前半段真的把台账写坏，后半段验证守卫拒绝写）。
2. **`record_curve` 必须按 step 去重。** 实测：不去重时，另一个写者已经记过的观测会被再写一遍，
   曲线变成 1、2、1、2。这不是"多了两条"——本模块自己的曲线校验器会直接拒绝它，
   而任何窗口统计都会照算不误。`observe` 是盲追加的（`:1110`），所以去重必须放在写者这一侧。
   用例：`test_the_sink_does_not_double_a_curve_another_writer_already_recorded`。
3. **`matched_steps` 必须放在 `PruneVerdict` 上**（设计稿只把它列在 `PruneDecisionRecord` 上）。
   `TrackerPruningSink` 只拿得到 verdict，凭一个 verdict 写不出忠实的决策记录。
   这是对 3.3 节的补充。
4. **`PruneSummary` 比设计稿多四个字段**：`running_indices`、`verified`、`unexplained`、`error`。
   设计稿只有 `unverifiable`，而一个字段无法区分"验过了、没问题"和"根本没验"——
   任务 6 要拿这些数字排序。"never raises" 也不该等于"什么都不说"。
5. **`verify_decision` 返回 `"verified" | "unverifiable"`，只在真矛盾时抛**（设计稿写的是
   `-> bool` 加抛）。R-4 那类规范化丢失——决策记着 `observed="nan"`，但曲线上的读数已被
   JSON dump 变成 `None`——不是"记录错了"，是"写者绕过了 `canonical_metric`"，报出来比抛出去对。
6. **遥测定位读 `TrialRecord.run_dir`，不猜目录名。** 设计稿 3.7 节说的是从
   `work_root/trials/<dir>` 里找；实测 `run_dir` 在 `pending` 时就写进记录了
   （`hyperparameter_search.py:1081`），试运行期间它已在盘上。比设计稿更简单也更稳。
   同节"两个都叫 log"的区分（`training.log` 是进程转发的 stdout、`train.log` 是训练器自己的）
   已由用例覆盖。

规模对照：设计稿估 520–640 行实现 + 560–720 行用例、55–70 个用例；
实际 **1690 行实现、2076 行用例、123 个用例**（`wc -l` 与 `--collect-only` 实测，2026-09-15）。
超出的是第 3.5/3.7 两节的参考适配器（台账审计的读写、JSONL 增量游标、遥测解析）——

## 10. 本设计的产生过程与被否掉的两个方案

三个独立设计（同一份实测事实、三个不同角度）→ 三名各自读码的评委（每人只评一份，验证对方的既有代码断言）
→ 一次合成。评分维度：可独立验证性、接缝契合、范围诚实度、风险、可演进性，各 0–10。

| 方案 | 总分 | 结局 |
| --- | --- | --- |
| POLICY-FIRST（纯核心 + 注入接缝） | 40.5 | 采纳为基底 |
| AUDITABLE VERDICT（判定即台账记录） | 37 | 融合（审计层与 `verify_decision` 保留） |
| ADAPTER-FIRST（复用产品规则与既有解析器） | 31 | 否 |

**评委对 AUDITABLE VERDICT 的两条致命反驳**（都成立，且第 1 条是实测的）：

1. 它的头号卖点"第三方只需台账即可重算"对 `is_nonfinite` 这条规则**是假的**：
   路径 `PruneWriter.observe → SearchTracker.observe:1096 → _supersede:267 → payload =
   {**previous.model_dump(mode="json"), **changes}:275`，非有限读数列化后变成 `None`，
   重算时 `is_non_finite(None) is False`，于是每一条 NaN 剪枝都会抛 `PruneAuditError`。
   本轮独立复现了这条（见 §9 的 pydantic 实测）。本文的处置是 R-4 选项 A（写入前规范化），
   并加了一条把该行为钉死的用例 `test_nonfinite_round_trips_through_the_ledger_shape`。
2. 它自己写的"已 open_run"守卫比它引用的守卫弱，而失败模式是**砖掉整个根**而不是丢掉一条记录。

**评委对 ADAPTER-FIRST 的反驳**（都成立）：

1. 它的复用论据建立在一个假前提上（"研究层必须重写解析器"），于是把约 150 行生产代码与一个
   永久性的双解析器漂移面算成了收益；
2. 它的四个模块没有装配点——生产路径里 `policy=None`，剪枝什么都不做，
   与它想替代的 0 调用者状态完全一样；
3. 它有两处用 "checked"/"measured" 措辞写的断言是假的。按本仓库的验收标准（"没有实际验证过的一律写未验证"），
   这一条扣分最重：验证一节不可信，后面的文件表也就不可信。

两个被否方案的完整正文没有被保留下来（工作流的子代理返回文本随会话目录一起清理）。
保留下来的只有本表里的结论与逐条可复核路径——它们已经足够，因为每一条都指向本次读过的具体文件行。
被采纳方案的正文就是本文第 1–9 节。
