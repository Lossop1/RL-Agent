# 控制台智能体 — 现状基线（agent baseline）

> 目的：在改任何东西之前，先把“现在到底有多慢、多准、多聪明”钉成可复现的数字，
> 让后面每一步改动都带着基线对比，而不是凭感觉。所有结论都来自真实日志、真实代码、
> 或对线上模型的真实调用。

## TL;DR（三个发现）

1. **响应**：一个问题不是一次调用，而是 **5–10 次串行**的大模型调用，单次中位 **24.8 s**、
   p90 **101 s**、最长 **214.7 s**。→ 一个问题**中位 ~111 s（约 2 分钟）、最坏 748 s（12+ 分钟）**。
2. **智能（最关键、也最便宜可改）**：模型**每次都在深度思考**（每调用产出 2500–6000 字的
   `reasoning_content`），但应用**只读最终答案字段（content，约 40 字），把思考整段丢掉**。
   于是你**花了全部思考的钱和延迟，只拿回一句被榨干的话**——而且在 5–10 跳里每跳都这样，
   包括“下一步该调哪个工具”这种根本不需要深思的琐碎决定。
3. **准确**：日志里反复出现“跑了 6–10 个工具、最后说‘我没有课程/门控的定义’”。
   而这些定义**代码里都有**（见下方金标准）；问题是 agent 的取证工具没把它们暴露出来。
   典型错例：用步数占比（如 15000/1500000≈1%）判断“还早”，而不是看课程阶段/门控。

## 一、它其实是怎么工作的（更正我之前的说法）

我早前说它“是一次性问答、算不上 agent”——**错**。日志证明它是一个 **ReAct 式工具循环**：
底层 `call_llm_with_schema` 确实是单发，但上层 `agent.py` 把它套进循环——每一步模型要么
输出 `{"tool": ...}` 去取一块证据、要么输出 `{"reply": ...}` 结束。证据由一个**确定性关键词
路由器**预先挑选并压进约 3500 字符的预算，再喂给模型（模型不能自己决定去看什么）。

## 二、响应基线（离线，来自 43 条真实调用日志）

`python -m autotuner.locomotion_console.agent_eval.analyze_audit`

| 指标 | 值 |
|---|---|
| 单次调用延迟 p50 / p90 / max | **24.8 s / 101.2 s / 214.7 s** |
| 每个问题的调用跳数 min/median/max | **1 / 5 / 10** |
| 每个问题墙钟 median / max | **111 s / 748 s** |
| 43 次调用中 超时 / 空答 | 2 / 2 |

病根：**每一跳都用 v4-pro 跑满一次深度思考**，即使那一跳只是“选下一个工具”。慢 × 串行 × 次数多。

## 三、冒烟枪：思考被生成后丢弃（线上实测）

同一个问题，直接打线上 `deepseek-v4-pro` 三种调用方式：

| 调用方式 | 耗时 | reasoning_content | content（应用唯一读取的字段） |
|---|---|---|---|
| 和应用一样（json_object） | 27.6 s | **2479 字** | **37 字** |
| 显式开思考 high | 74.6 s | 4739 字 | 59 字 |
| 普通调用 | 92.9 s | 6127 字 | 55 字 |

结论：**思考默认就在跑（这就是 25–100 s 的来源），但应用只读 `content`、从不读 `reasoning_content`。**
你为思考付了全部延迟，却把 98% 的思考成果扔掉了。这一条同时解释了“慢”和“答得浅”。
（附带更正一个我自己制造的假警报：日志里中文看着像乱码，程序化核对后确认是我终端显示问题，
存储与喂给模型的内容是干净 UTF-8，不是 bug。）

## 四、准确基线（A 金标准 / B 反例）

线上直连模型的评测结果见 `baseline_results.json`（由 `run_eval.py` 生成）。
注意 `run_eval` 会对 A 类打两个分：**应用可见分**（只看 content）与**模型实产分**（content+reasoning），
两者之差 = 被丢掉的思考值多少分。

**直连线上模型（开思考、无证据工具、只给问题本身）——这是“模型裸考”的地板分：**

| 用例 | 得分 | 说明 |
|---|---|---|
| A1 门控阈值 | **0%** | 0.60/0.70/6.0 这类**配置里的具体数字，模型没证据就猜不出** |
| A2 惩罚渐入 | 75% | 名字能推（penalty_ramp_intervals、线性、封顶1.0），答得不错 |
| A3 actual_vx | 25% | 部分对 |
| A4 地形推进 | 50% | 结构对，细节缺 |
| A5 等级3楼梯高度 | 20% | num_rows=10、区间值猜不出 |
| **A 类总体** | **34%** | 越是项目专属的确定值，越答不出 |
| B 反例 | **挂**（0/1） | 即使提到“阶段”，**仍然用 0%/1% 步数占比说事** |

两个关键解读：
1. **准确性瓶颈在“取证”，不在模型智商。** 能靠名字推的（惩罚渐入）到 75%；纯配置数字（门控阈值）
   是 0% —— 模型不可能凭空知道你配的 0.60。**必须由证据工具喂。** 而日志显示：工具经常喂不到
   （跑了 10 跳还说“没有定义”）。这正是准确性的病根。
2. **连前沿模型默认也会犯那个错**（B 挂）——步数占比的错位不是模型笨，是没被系统提示/证据掰过来。

附带一个反向印证：本次直连**没有强制 JSON**，于是 `content` 是完整答案、app 分==model 分（无丢失）。
反过来说明——**别在综合那步强制 JSON，答案就能完整落到 content 里**；应用现在那句被榨干的话，
正是“强制 json_object + 只读 content”造成的（对照第三节的 37 字 content）。

## 五、金标准答案（A 类 — 代码为证，可直接当验收锚点）

- **A1 各阶段门控阈值** — `taili_amp_env_cfg.py:226–233`, `taili_amp_env.py:939`
  phi0→phi1 方向 progress 最小值 **≥0.60**；phi1→phi2 **≥0.70**；phi2→phi3 progress **≥0.50** +
  平均地形等级 **≥6.0** + 摔倒率 **≤0.05**；且都要求 `penalty_gate` 已到 **1.0** 并连续
  `phase_intervals` 次满足。`slip_1=0.20` 为历史字段、已不作门控。
- **A2 惩罚渐入（penalty_gate）** — `taili_amp_env.py:214,878–884`, `cfg:225`
  0→1 线性渐入：`step = 1/penalty_ramp_intervals`（配置 `penalty_ramp_intervals=25`，即每步 +0.04），
  达标继续加、回退则减，封顶 1.0；`phase≥1` 时自举为 1.0。用于按比例混合质量惩罚强度，避免早期 critic 冲击。
- **A3 actual_vx** — `blind_tp_env.py:1427`
  `float(vb[:,0].mean())` = 机身坐标系下基座线速度的前向(x)分量、对所有并行环境取均值。实测前进速度，用于对比命令速度。
- **A4 地形推进策略** — `taili_core/terrain_curriculum.py:13–135`
  逐环境升降级。**升级**需一次“稳定通过”：走够距离(`dist>terrain_move_up_dist`) 或 受控高度上下变化，
  且结尾稳定（直立 + 基座高度够 + 足接触够 + 机身角速度低）并速度受控。**摔倒/终止/失稳=立即降级**；
  走得比预期少也降级。地形仅在 `terrain_start_phase` 之后启用。单纯高度变化不算成功，冲下楼梯判为失败。
- **A5 地形等级3 楼梯高度** — `taili_amp_env_cfg.py:17–37`
  共 `num_rows=10` 个难度等级(0..9)，台阶高度随难度在各自区间内插值。等级3→难度 3/9≈0.333：
  矮楼梯子地形 ≈ 0.05+0.333·(0.15−0.05) ≈ **0.083 m**；高楼梯子地形 ≈ 0.08+0.333·(0.30−0.08) ≈ **0.153 m**。
  **不是单一数值**，取决于是哪种楼梯子地形。

## 六、反例（B 类）
问：“现在训练到 15000/1500000 步，接下来调参策略怎么定？”
**判错标准**：用步数占比说“还早/太早/才 1%”。**判对标准**：落到当前阶段、门控差距或阻塞项上。
理由：进度由课程阶段/门控决定，不由绝对步数比例决定。

## 七、据此重排的改法（证据 → 优先级）

1. **停止在便宜的跳上思考**（最高杠杆、最便宜）：工具选择那种跳用非思考/小模型（如 `deepseek-v4-flash`），
   只在最终综合那一步开思考。直接砍掉大部分 25–100 s 的浪费。
2. **把思考读出来/用起来**：最终答案那一步读 `reasoning_content`，别再只留一句被榨干的 content。
3. **给 agent 的工具补上它现在看不到的事实**（门控值、课程/地形定义）——这些前端已经能显示，agent 却取不到。
4. **减少串行跳数**：能确定性批量取的证据就别一跳一跳问模型。
5. **流式**：思考更慢，不流式体感更差；流式把体感救回来。

## 八、如何复现
```
# 响应基线（离线，免费）
python -m autotuner.locomotion_console.agent_eval.analyze_audit

python -m autotuner.locomotion_console.agent_eval.run_eval --with-facts # 注入事实卡后
```

## 九、第一步改动 + 实测效果（准确优先）

改动：新增 `curriculum_facts.py` —— 一张代码推导的**事实卡**（门控阈值、惩罚渐入、actual_vx、
地形升降级、地形等级/楼梯高度，约 1000 字、带代码出处），并把它**每轮常驻注入 agent 上下文**
(`agent.py::run_agent`)，让 agent 不用花跳数去取这些事实，也不容易滑到步数占比那个错。
provider 有单测（`tests/.../test_curriculum_facts.py`），控制台测试套件 62 项全绿。

**同一批问题、同一个模型，注入事实卡前后对比：**

| | A 类准确率 | A1 门控值 | 单题延迟 |
|---|---|---|---|
| 注入前（裸考） | **34%** | 0% | 23–78 s |
| 注入后（事实卡） | **100%** | 100% | **4–11 s** |

一箭双雕：**又更准、又更快**（模型直接引用事实卡，不用再靠推理去猜，所以反而更快）。
B 反例：注入后模型开始**引用阶段/门控**了（方向对了），但仍会带一句“1%”，严格判定仍算没过——
说明步数占比这个坏习惯的抑制还要再加力（提示更硬，或评分口径再议）。

> 说明：这是“模型拿到事实卡”的证明。同一张卡现在已接进真实 agent 的每一轮上下文，
> 生产链路同样受益；但真实 agent 的端到端时延要连着远程后端才能测，本机只验证到
> provider 单测 + 模型层实测 + 控制台套件全绿。下一步（按更高目标）：把“选工具”那种
> 不用思考的跳降级到快模型、并在最终综合那步读 `reasoning_content`，把响应再压下来。

## 十、第二步改动：思考不再在网关层被丢掉（item #2 地基）

背景（第三节的冒烟枪）：`content` 在 `response_format=json_object` 下被榨成一句话，实质落在
`reasoning_content`——而网关 `call_llm_with_schema` 只读 `message.content`，思考**在最底层就被丢弃**，
上面任何一层都不可能再用到。这是“花了思考的钱只拿回一句话”的结构性根因。

改动（最小、可逆、只补管道、不动已验证的路由）：
- `llm_gateway/client.py`：`LLMResponse` 新增 `reasoning` 字段，从 `message.reasoning_content` 捕获
  （`getattr` 兜底，普通模型没有该字段则为 `""`，不破坏任何下游）；同时写进审计日志。
- `agent.py`：`run_agent` 两个终答出口（最终 `reply` / 待确认动作）把 `resp.reasoning` 带出到返回值，
  思考不再在 agent 层丢失。
- 单测 `tests/autotuner/llm_gateway/test_reasoning_capture.py`：捕获思考、缺字段兜底为空、`model=` 覆盖
  确实传到 API 三种情况；网关+控制台+taili_core 套件 65 项全绿。

实测证据（`results_with_facts.json` 里快模型每跳 `reasoning_chars` 46–667）：思考**确实存在且非空**，
先前是被网关整段扔掉——现在起被保留。

**尚未闭合、需要拍板的岔口（不擅自选、以免漂移）**：思考已被**保留**，但还没被**消费**——
`out["reasoning"]` 目前到 app 层为止没人读。怎么用它有真实取舍：
1. 直接展示给操作员？——可能与控制台“只讲事实、不下判断”的设计原则冲突（模型思考含推测/判断）。
2. 最终综合单独走一次“不强制 JSON + 思考模型”的调用，把实质灌进答案（第七节 1/2、第四节脚注的做法），
   但会给每题加一次思考调用的时延——与当前 all-flash（事实类已 100%、2–4 s）是速度 vs 深度的取舍。
3. 只作内部用途（如落审计/接地校验），UI 不变。
B 反例（“1%”）仍挂，作者自评“评分口径再议”：模型其实已引用 阶段/gate/门控（方向对），
只因附带提了“1%”被子串命中判失败——属于评分器过严还是提示要更硬，也是一个待定口径。
